# 离线播报与本地意图控制：实现笔记（2026-09-20）

这篇记的是**板子怎么在不联网的前提下听懂一句话并真的把设备控制掉**，
以及中间那些"看着能跑、实际不行"的坑。写给下次要在这个平台上做同类事情的人。

---

## 一、先把"听懂"和"知道该干什么"分开

一开始的诱惑是"塞个更大的语言模型进网关"。算了一下不划算：这块 ESP32-S3
除了推理还要当 PPP 服务端和 NAT 出口，剩下的内部 RAM 只有几百 KB（模型权重放
PSRAM，但运行时缓冲和 lwIP 的 pbuf 池都在内部 RAM 里抢）。而"听懂了要干什么"
本质是**闭集分类**——动作就那么几十个，根本不需要生成能力。

于是链路切成两段：

```
一句话  ──►  意图分类器（65 类，标签就是动作 JSON）  ──►  动作执行（局域网 UDP）
```

分类器小到可以完全离线：字符 1–3 gram 的 CRC-32 哈希袋（4096 维）+ 线性 softmax，
权重压成 int8 只有 **780 KB**，而且是 `static const`，直接编进固件。
片上推理一句中文只有几十个非零特征，点积是稀疏的，毫秒级。

**为什么量化是安全的**：推理只要 `argmax`。整矩阵乘一个正数不改变谁最大，所以
"除以最大绝对值再取整"这种最粗暴的量化就行，不需要校准集。这一点值得记下来——
**先想清楚推理到底要什么，再决定量化精不精**。

## 二、语料是真正的瓶颈，而且错法会告诉你缺什么

第一版中文留出集 93.8%，看着不错。但真机批测 15 句错了 6 句，错法非常整齐：
`关闭台灯`、`关闭客厅的灯` 全被判成**开灯**，而 `关灯`、`把台灯关掉` 是对的。

翻语料就明白了：蒸馏来的"关"族说法有 44 条，句句是 `关了 / 关一下 / 关掉 / 关空调`，
**没有一条用"关闭"这个动词**。模型不是学错，是**没见过**。补了 60 条手工说法
（单独一个文件，和蒸馏语料分开存，好在仓库里分清来源），中文留出集变成 **16/16**。

第二轮又抓到三个**方向性**错误：`把台灯调到最亮` → 亮度 30、`台灯调到最暗` → 80。
这类"极值词"要靠专门的说法喂进去，于是又补了"最亮/最暗/百分之五十/太暗了"这一批。

**两条经验**：
1. 留出集准确率高 ≠ 能用。**必须拿真人会说的句子去批测**，错法本身就是诊断信息。
2. 语料要**按来源分开存**（模板 / 蒸馏 / 手工），否则你无法回答"这条错误是哪种
   来源缺了"。我们为此给训练脚本加了 `--extra`，把原来手工做的合并步骤写进流水线。

## 三、板子"会说话"分两条路，别混为一谈

| 要说的内容 | 走哪条 | 断网时 |
|---|---|---|
| 固定短语（开/关/调好/没回应…） | 预合成片段，存在 `/etc/clips` | **能说** |
| 任意文本（"今天天气不错"） | 云端 TTS 合成 | **不能说** |

固定短语这条路的关键认识是：**合成可以在 PC 上联网做，播放可以完全离线**。
片段是数据不是代码，直接入库，编进 romfs 就行。成本是 flash（16 条 ≈ 710 KB），
收益是断网演示时设备真的会出声。

接法很轻：`voice_say_text()` 开头加一张"句子 → 片段"表，命中就走 `/etc/clips`，
未命中保持原样（走云端）。**关键改动只有十几行**，但没有它，离线演示里板子就是个哑巴
——屏幕上有字、喇叭里没声，这在演示里非常刺眼。

**边界要写清楚**：带数字的句子（"亮度已调到 80"）播的是通用句（"台灯亮度已调好"）。
为每个取值预合成不值得占的 flash；屏上仍然是精确的 80。

## 四、被控端用官方模拟器，是为了让证据站得住

自己写个 UDP server 收下自己的包，然后说"我控制了米家设备"——这不叫验证，
叫自证。所以被控端用 **python-miio 自带的官方模拟器**
（`miiocli devtools miio-simulator --file <yaml>`），它由官方代码实现协议，
日志里会自己打印收下了什么调用：

```
Got setter call {'method': 'set_power', 'params': ['on', 'smooth', 500]}
```

**这行日志是官方代码执行了我方指令的直接证据**，比任何自测截图都硬。

顺带踩到两个坑，记下来省别人的时间：
1. **官方模拟器的 token 是固定全零的公开常量**（源码里写死 `32 * "0"`）。
   我们设备表里另一台设备配了别的 token，于是那台永远"没有回应"——
   token 对不上就解不开回包。排查时先怀疑 token，再怀疑代码。
2. 官方模拟器端口写死 54321，**一台主机只能起一个实例**。要同时演示"两台设备"，
   只能让两个设备名指向同一个实例——这一点必须在文档和视频里说清楚，
   不能让别人以为你监控了两台真设备。

## 五、协议细节：别照文档猜，去和参考实现对拍

miIO 的报文结构看着简单，但有一处约定如果猜错，协议就永远谈不通：
**校验和覆盖的是密文**（`MD5(header16 + token + ciphertext)`），不是明文。

我们的做法是写一个对拍脚本（`pc_side/miio_protocol_check.py`），直接调用参考实现的
`Message.build/parse`，把同一组字段分别喂给两边，逐字段比对。比明文而不是比密文——
因为 JSON 的空格顺序不同会导致密文必然不同。**这类"必须和参考实现对拍"的地方，
一定要对拍，不要读文档**。

## 六、串口工具会把板子按死（这段最坑）

调试期间板子反复"失联"：**串口只剩回显，任何命令都没有输出**。
一度以为是板子坏了，其实是串口工具的手握信号在作怪：本板把 USB-UART 桥的
**RTS 接进了自动下载/复位电路**，工具在打开端口时把 RTS 拉错电平，就把芯片按在了
ROM 下载态——表现就是"能收到回显（ROM 的 shell 在回显），但什么都不执行"。

三条实用结论：
1. **用仓库里 `pc_side/serial_tcp_bridge.py` 或 `nsh.py`**，它们开端口后不碰 DTR/RTS。
   手工 pyserial 千万不要自己"纠正"这两根线的极性——我们为此浪费了一小时。
2. 软件侧救活只要 10 秒，不必重烧整包（约 5 MB，要几分钟）：
   ```bash
   sftool -c SF32LB52 -p COM5 -b 1000000 --before default_reset --after soft_reset \
     read_flash x.bin@0x12010000:0x100
   ```
   `--after soft_reset` 是把芯片从下载态里带出来的关键那一步。
3. 复位板子会丢掉 PPP 会话；**S3 复位后板子的 `pppd` 必须重起**（换说法再问也不行）。

## 七、演示前真机链路的"体检清单"

按这个顺序做，能避开九成的临场故障：

1. PC 上先起官方模拟器（终端留着，它就是证据画面）。
2. 复位一次 S3（它的 httpd 跑久了会拒绝新连接，已知缺陷）。
3. 板子：`pppd /dev/ttyS0 460800 &` → `ai_agent` →
   `set_llm http://10.0.0.1/v1/chat/completions cmd local`。
4. 先问一句**训练集里没有的说法**（例如"把台灯打开"），确认上屏 + 播报都正常。
5. 每句都要换说法——Agent 会缓存同一个问题，第二次直接返回旧答案、根本不发请求。
6. 万一"只有思考中没有答复"（已知的间歇症状）：**原样再问一次**，命中缓存会立即派发。

## 八、这一轮之后仍未解决的

- 板子 `ask` 后的间歇崩溃（`sched_dumpstack`）没复现到断言原文，**未定位**。
- 上述"答复不派发"的间歇症状，同样**未定位**。
- S3 的 httpd 跑一段时间后拒绝新连接（板子经 PPP 不受影响），复位即恢复。
- 云端 TTS（念任意文本）在板上仍未打通：经 PPP 的大响应会被截断，
  未定位到 `pppos_input_tcpip failed with -1` 的确切原因。
- 被控端是官方模拟器，**真台灯未验证**；真机迁移只差设备表一行（IP/token）。
