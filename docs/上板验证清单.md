## Step 0：环境自检（5 分钟，**别跳过**）

本机实测踩到两个坑，都会让编译直接失败。**在非交互 shell 里跑脚本时尤其要注意**——
下面两个目录都不在默认 PATH 里（`.bashrc` 第 120 行把 PATH 整个覆盖了）：

| 缺什么 | 报错 | 位置 |
|--------|------|------|
| ARM 工具链 | `/bin/sh: 1: arm-none-eabi-ar: not found` | `~/arm-tc-root/usr/bin` |
| kconfiglib 的 `olddefconfig` | `FATAL_ERROR: Kconfig environment depends on kconfiglib` | `~/.local/bin` |

```bash
export PATH="$HOME/arm-tc-root/usr/bin:$HOME/.local/bin:$PATH"

# 自检
which arm-none-eabi-gcc arm-none-eabi-ar olddefconfig
arm-none-eabi-gcc --version | head -1      # 期望 13.2.1 20231009
olddefconfig --help >/dev/null 2>&1 && echo "kconfiglib ok"
```

**通过标志**：三个路径都打印出来，gcc 版本为 `13.2.1 20231009`。

> 交互式登录终端（你平时敲命令的那个）通常已经带上了这两个路径；
> 但用 `wsl bash xxx.sh` 这种非交互方式跑脚本时必须显式 export，否则必挂。

## Step 1：编译（10–30 分钟）

```bash
cd /home/lawson/openvela
```

`grep CONFIG_SYSTEM_NXRECORDER out/.../.config` 仍显示 `not set`，固件大小也和改动前一模一样。

2. 配置生效：`grep CONFIG_SYSTEM_NXRECORDER out/.../.config` → `=y`
3. 驱动进了固件符号表：

```bash
grep -c "sf32lb52_audio\|audio_register" out/sifli_sf32lb52_devkit_lcd_nsh/System.map
# 期望输出 5（sf32lb52_audio_initialize / getcaps / configure / audio_hw_init / audio_register）
```

## Step 2：烧录（10 分钟）

`sftool` 是思澈官方烧录工具，**当前 WSL 里没有装**（`which sftool` 为空，pip 也没有）。
先从思澈 SDK / 官方渠道拿到 `sftool`，确认可用后：

```bash
sftool -c SF32LB52 -p /dev/ttyUSB0 -b 1000000 \
       --before default_reset --after soft_reset \
       write_flash out/sf32lb52_devkit_lcd_nsh/../../out/sifli_sf32lb52_devkit_lcd_nsh/nuttx.bin@0x12010000
```

> 上一条命令里的路径请直接写绝对路径，避免相对路径歧义：
> `write_flash /home/lawson/openvela/out/sifli_sf32lb52_devkit_lcd_nsh/nuttx.bin@0x12010000`

**通过标志**：sftool 打印写入进度并完成，无 `Failed to connect to the chip`。

**踩坑点 1**：`Failed to connect to the chip` = SoC 错过了 RTS 复位后约 2 秒的 `ATSF32` 监听窗口
→ 重新插拔 USB，或按板载 Reset 键后立刻重试。

**踩坑点 2**：在 WSL 里访问 USB 串口需要 `usbipd` 把设备转发进 WSL，或直接在 **Windows 侧**跑烧录工具。
若 `ls /dev/ttyUSB*` 看不到设备，就是这个原因——改用 Windows 侧终端（模块/COM 口）执行烧录。

## Step 3：串口控制台（5 分钟）

```bash
picocom -b 1000000 --noreset --lower-rts --lower-dtr /dev/ttyUSB0
```

**⚠️ 绝对不要用 `screen` 或 `cu`**：本板把 USB-UART 桥的 RTS 直接接到 VCC 负载开关，
这两个工具没有 deassert RTS 的能力，会让芯片**一直停在复位态**，看起来像"板子坏了"。
`minicom` 会在连接时复位一次但之后正常，可用。

**通过标志**：看到 `SFBL` → NuttX 启动日志 → `nsh>` 提示符。

## Step 4：采集证据（核心环节，30 分钟）

### 证据 A：`/dev/audio0` 存在（证明 M1）

```text
nsh> ls /dev
```

**对照点**：官方板级 README 里的示例输出**没有** `audio0` 这一行，我们的输出**有**。
把两条并排截图 —— 这是"适配前 vs 适配后"最有力的证据。

**⚠️ 它为什么在 `/dev` 根下而不是 `/dev/audio/` 里**：NuttX 的 `audio_register()`
只接受设备**名**，自己拼成 `/dev/audio/[name]`（`nuttx/audio/audio.c:1793-1835`）。
我们通过 `CONFIG_AUDIO_CUSTOM_DEV_PATH=y` + `CONFIG_AUDIO_DEV_ROOT=y` 选了 NuttX
为此提供的 "simple case"，路径变成 `"/dev/" + name`，所以最终就是 **`/dev/audio0`**，
且不需要预先创建 `/dev/audio` 目录。（早期版本传了完整路径，算出的是
`/dev/audio//dev/audio0`，注册会以 `-ENOENT` 失败、设备根本不出现——这个坑已修，见排查表。）

```bash
# 留存原始日志（在 Linux 侧用 tee 记录整个串口会话）
picocom -b 1000000 --noreset --lower-rts --lower-dtr /dev/ttyUSB0 | tee ~/audio_verify.log
```

### 证据 B：硬件真被配置（证明 M2）

```text
nsh> nxrecorder
nxrecorder> device /dev/audio0
nxrecorder> recordraw /data/test.pcm
```

> **⚠️ 录音要写到 `/data`，不是 `/var`**（实测更正）：本板挂载的是
> `tmpfs → /data`、`romfs → /etc`、`procfs → /proc`，**没有 `/var` 目录**，
> 写到那里会报 `File ... not found`（父目录缺失）。
> `df -h` 显示 `/data` 只有 512B 是**显示假象**——NuttX 的 tmpfs 是从堆动态分配的，
> 实测写 270 KB 毫无问题。

**命令说明**（已核对 `nxrecorder_main.c:97` 的命令表，没有 `open` 这个命令）：

| 命令 | 作用 | 注意 |
|------|------|------|
| `device <路径>` | 指定音频设备 | 必须给**完整路径** `/dev/audio0`；给裸名字它会去试 `/dev/audio/<名字>`，对不上 |
| `recordraw <文件>` | 录成 PCM 裸数据 | 最简单，不需要编解码器 |
| `record <文件>` | 录成媒体文件（按扩展名判断格式） | 依赖 mp3/amr 等编码，先别用 |
| `stop` | 停止录音 | |
| `q` / `quit` | 退出 | |
| `h` / `help` | 帮助 | 现场忘了命令就敲这个 |

预期串口输出（M3 已实现）：

```text
capture config: 48000Hz 2ch 16bit              ← ✅ M2 核心证据：寄存器真被配过
capture started (staging 16384 B, circular)    ← ✅ M3：环形 DMA 已挂上暂存区
```

> 速率/声道数由**主机请求**决定（`nxrecorder` 默认用 48000Hz/2ch；这是实测到的值）。
> 想录 16kHz 单声道就在 nxrecorder 里显式指定，具体命令见 `h`。

**怎么读这两行**：

- 第一行由 `sf32lb52_audio_hw_config_capture()` 打印，**它在打印之前已经真的往
  AUDCODEC 的 ADC 通道寄存器和 AUDPRC 的 RX0 通道写完了配置值、并按 16kHz 设置了时钟分频**。
  所以这行日志 = 硬件真被配置过的证据，不是纸上谈兵。这是 M2 最硬的证据。
- 第二行说明环形 DMA 已在 16 KiB 双半暂存区上跑起来了。

**录音是否真的出数据，这样判定**：

```text
nxrecorder> recordraw /data/test.pcm
nxrecorder> stop
nsh> ls -l /data
```

- **文件存在且大小明显大于零** → 录音链路通了。**实测值供参考**：默认 48kHz/2ch/16bit
  （192 KB/s）下录到 **270,336 字节**（33 个 8 KiB 缓冲）。若按 16kHz/1ch/16bit 配置，
  即 32 KB/s，录 3 秒约 96 KB。这是 M3 通的**决定性证据**。
- **想进一步确认不是全零**：`hexdump /data/test.pcm`，看采样值是否平滑连续变化。
  全零 = 模拟通路没通；乱码 = 时钟配错；平滑波形 = ADC 在真实转换。
- 文件为 0 字节或不存在 → 数据通路没通，按排查表走。
- 若打印 `overruns` 大于 0（`stop` 时会打 `stop: overruns=N`），说明上半身供桶不及时，
  数据被丢弃——加大 `CONFIG_AUDIO_NUM_BUFFERS` 可缓解。

**放音验证**（需要接 4Ω 喇叭到 SPK 座）：

```text
nsh> nxplayer
nxplayer> device /dev/audio0
nxplayer> playraw /data/test.pcm
```

录下来的 PCM 直接回放，能听到声音即放音链路通。**注意听有没有"砰"的爆音**——
如果有，说明防爆音时序需要复查（这是我们逐行对齐官方驱动的部分，首次上板正是验证它的时机）。

> ⚠️ **录音要写到 `/data`**：本板挂载的是 `tmpfs → /data`、`romfs → /etc`、
> `procfs → /proc`，**没有 `/var`**，写到那里会报 `File ... not found`。
> `df -h` 显示 `/data` 只有 512B 是**显示假象**——NuttX 的 tmpfs 从堆动态分配，
> 实测写 270 KB 毫无问题。

## 排查表

| 现象 | 原因 | 处理 |
|------|------|------|
| `arm-none-eabi-ar: not found` | 非交互 shell 未加载 `.bashrc` | `source ~/.bashrc` 或显式 export PATH |
| `Failed to connect to the chip` | 错过 ATSF32 监听窗口 | 重插 USB / 按 Reset 重试 |
| `ls /dev/ttyUSB*` 为空 | WSL 未转发 USB | 用 usbipd 转发，或改在 Windows 侧烧录 |
| 串口无任何输出 | RTS 被拉低，芯片停在复位 | 换 picocom，加 `--noreset --lower-rts --lower-dtr` |
| 有 NSH 但 `ls /dev` 没有 audio0 | **注册路径错**：传了完整路径而非裸名 | 确认 `.config` 里有 `CONFIG_AUDIO_DEV_ROOT=y`，且 `sifli_ap.c` 里是 `audio_register("audio0", ...)` |
| 用 `cat /dev/audio0` 没有任何输出也没报错 | **方法错**：`audio_read` 是空壳，`ops->read == NULL` 时直接 `return 0`（`audio.c:305-310`），表现为立刻 EOF | **改用 `nxrecorder`**，它才会走 CONFIGURE/START 的完整流程 |
| `nxrecorder` 报 `-EPERM` | 没先 CONFIGURE 就 START | 用 `nxrecorder` 的正常流程（它会自动 CONFIGURE）；或在自研程序里先 `ioctl(AUDIOIOC_CONFIGURE)` |
| `nxrecorder` 命令不存在 | `CONFIG_SYSTEM_NXRECORDER` 未生效 | 确认 `apply.sh` 已覆盖 defconfig，且**删掉 `out/` 重新配置**后再 `m` |
| 编译报 `-Werror` 相关错误 | `drivers/CMakeLists.txt` 未覆盖 | 重新执行 `apply.sh` |
