# 米家生态控制方案（软件层先行，上板再验证）

> 状态：**软件设计 + 待实现/待验证**。本文不含任何实测结论；凡是没上板跑过的，
> 一律标注"待验证"。写它的目的是先把分工、改动点、验证顺序钉死，再动硬件。

## 0. 一句话

板子（主控：语音、屏幕、喇叭、说与不说的决定）──PPP 小 JSON──▶ S3（本地模型 +
miIO 局域网客户端 + NAT）──WiFi 局域网 UDP:54321──▶ 米家设备。
**这条路不需要小米云，也不需要外网**：断网时"听懂 → 控制 → 播报"整条链仍然成立。

## 1. 为什么走得通（已核实的既有事实，不是设想）

| 事实 | 依据 |
|---|---|
| S3 模组是 **N16R8**：16 MB flash + 8 MB PSRAM（Octal 80 MHz） | 网关 `partitions.csv` 注释 + `sdkconfig`（`CONFIG_SPIRAM=y`、`SPIRAM_MODE_OCT`） |
| 当前 app 镜像 **1,141,280 B / 3 MB**，另有 **8 MB `llm` 数据分区**专放模型 | `build/sf32lb52_wifi_gateway.bin` + `partitions.csv` |
| 网关已链入本地模型栈 **espllm**（llama2.c 移植），并把 `model:"cmd"` 交给本地动作执行器 | `main/CMakeLists.txt`（REQUIRES espllm）、`net_cloud.c:326`、`gateway_main.c:108/120` |
| 命令模型是 **0.26M 参数的闭集动作分类器**，输出动作 JSON，留出集 43/46 | `cmd_exec.c` 头部注释、`esp32s3_common/assets/cmd_llm*.bin` |
| 动作表已覆盖 led/wifi_scan/ping/status/temperature/time/weather/ask，与数据集脚本对齐 | `cmd_exec.c`、`esp32s3_common/tools/make_cmd_dataset.py` |
| 板子能直接打到网关的 HTTP 端点（PPP 内网 `10.0.0.1`，TLS 1.2 通） | 本项目上一轮实测日志 |
| 板子↔S3 这条腿只传小 JSON（几百字节），**不受"大响应 20 KB 截断"的影响** | 本项目 `docs/AI-Agent端到端实测证据.md` 第七节 |
| miIO/MIoT 是**局域网 UDP 54321**，握手后 AES-128-CBC；ESP-IDF 自带 mbedTLS（AES/MD5）与 cJSON | 协议公开实现（python-miio）+ ESP-IDF 自带组件 |
| S3 已有 HTTP 服务与路由钩子 | `espllm.h` 的 `espllm_set_router`、`espllm_http.c` 的 `kUris` |

## 2. 分工（谁做什么）

| 角色 | 负责 | 不负责 |
|---|---|---|
| **板子（SF32LB52，主控）** | 麦克风/喇叭/屏幕；把用户的话送到 S3；把返回的动作变成"中文上屏 + 语音播报"；决定说什么 | 不碰米家协议、不存 token、不做推理 |
| **S3（ESP32-S3）** | ① 本地意图模型（文本→闭集动作 JSON）② miIO 局域网客户端（真正发指令）③ PPP/NAT 网关 | 不负责语音合成（板子做）、不暴露在公网 |
| **米家设备** | 执行（台灯开关/亮度/色温…） | — |

**为什么 miIO 客户端放在 S3 而不是板子**：S3 本来就在局域网上（有 WiFi 口），
mbedTLS/cJSON 都在；板子要发 UDP 得穿过 PPP 的 NAT 回程，多一层不确定性，而板子
的价值在语音与交互。**"结果回板子、板子做主控"这条原则不变**：S3 执行完把结果
（成功/失败/状态）作为动作结果返回，板子决定怎么念、怎么显示。
（若坚持要板子亲自发 UDP，方案不变、只是把 `net_miio.c` 的调用点从 S3 挪到板子
的 `action_speak.c` 旁边，代价是板子侧要自带 MD5+AES 与 UDP 回程调试。）

## 3. 软件改动清单（逐文件）

## 4. 验证顺序（重要：先软件、后模拟器、再真设备）

1. **PC 侧协议闭环（不需要板子）** —— 已完成，见 `docs/ESP32-S3网关台架实测证据.md`：
   官方模拟器在 python-miio 0.5.12 里已被移除，所以做法是 ① 用 python-miio 的参考实现
   `miio/protocol.py` 逐字段对拍 net_miio.c 的报文（含"checksum 按密文算"这条关键约定）
   ② 自写最小设备模拟器（`pc_side/miio_device_sim.py`）并用**参考实现自己的客户端**
   驱动它，确认它是一台标准 miIO 设备。剩下的"真机"半步由换 IP/token 完成。
2. **S3 重烧**：网关固件现在板上那版还没有 `cmd`/espllm 分支，必须先 `tools/flash.bat`
   （需要 S3 的 USB 接电脑）。
3. **板子端到端**：板子 `ask 打开台灯` → 屏幕中文 + 喇叭播报 + 台灯（模拟器）状态变化。
4. **真设备**：`miiocli cloud` 取 IP+token（**一次性、只落到被 gitignore 的 sdkconfig**）
   → 把设备表那一行换掉即可，代码与模型不用动。

## 5. 资源与模型的实话（你点名的那件事）

- **控制任务不该靠堆参数**。当前 0.26M 参数的闭集分类器就是对的形态：动作 JSON 只有
  十几个 token，延迟低、可解释、可评分。真正的短板是**语言覆盖**（语料是英文）和
  **动作词表**（没有米家），不是容量。
- 资源账：8 MB PSRAM + 8 MB `llm` 分区基本是空的。要放大，可行的是**2–5M 参数**
  （dim 512 / 8 层 / 中文词表 4096）放 PSRAM，q8 约 2–5 MB。代价是延迟从"亚秒"涨到
  "数秒"——控制类交互要**先保延迟**，所以建议：先扩语料与动作，模型规模按留出集
  准确率决定，不为了"塞满"而塞满。
- **该把资源花在哪：设备端语音输入**。现在指令还是打字进去的，"断网可用"最硬的短板
  是**离线 ASR**——板子有麦克风，S3 有算力与 PSRAM，方向是小型流式 ASR（或先做
  关键词/命令词识别）。这件事对"断网也能用"的价值，比把控制器从 0.26M 堆到 20M 大得多。
- **不做的事**：不复活讲故事的模型；不让模型自由生成指令（闭集 JSON 是安全边界）。

## 6. 兼容性与风险（如实写）

- **不是所有米家灯具都支持局域网控制**。Yeelight 系 Wi-Fi 照明与米家台灯一代
  （MJTD01YL）支持；米家台灯 1S 等新固件据用户反馈已移除"局域网控制"开关。
  判断方法：设备设置页找"局域网控制/LAN 控制"，可启用即支持。
- **S3 必须和目标设备在同一局域网**。现在 S3 连的是手机热点；要做米家控制，得把
  S3 换到家里路由器那张网（改 `sdkconfig` 的 SSID/密码，`tools/set_wifi.py` 写入，
  凭据不入库）。
- **token 是凭据**：等价于那台设备的钥匙。只进被 gitignore 的 `sdkconfig`/NVS，
  绝不进仓库、不进聊天、不进日志。
- **未验证就先说未验证**：本文所有内容在 `model:"miio"` 分支跑通前，都只是设计。

PC 模拟器 + 板子：`ask 打开台灯` → 屏幕显示"台灯已打开" + 喇叭播报 + 模拟器的状态

## 8. 评审口径与上板前的必测项（2026-09-20 补充）

### 8.1 赛道归属（主动说明，不等被动归类）

本作品横跨两条线，写在这里以免误判：

- **底层**：为黄山派（SF32LB52-DevKit-LCD）在 openvela/NuttX 上补全音频驱动接口
  （`audio_ops_s` + 三处 `ioctl` 语义），属于"新硬件适配"路径 B；
- **上层**：S3 上的本地意图模型 + miIO 局域网控制 + 端云协同，属于"AI 硬件产品创新"。

两条线的证据分别在 `board/sf32lb52_audio/`（含 `patches/0005-*.patch`）与本文档；
请组委会据此判定归属。

### 8.2 上板前必须测的两件事（顺序不要反）

1. **网络可达性（做第 4 节步骤 1 之前）**：PC 接入手机热点后先确认与 S3 的互通性。
   真正必需的方向是 **S3 → PC:54321/udp**（模拟器跑在 PC 上）；PC → S3 不通只影响
   调试便利，不影响演示。若两个方向都不通（部分安卓热点隔离客户端），立刻改成
   "PC 开热点"或家里路由器，**不要拖到上板那一步才发现**。
2. **PPP 链路小包稳定性（第 4 节步骤 3 之前）**：连续发 100 条几百字节的 JSON，
   记录成功率与往返延迟。控制指令全走这条链路，**稳定比快重要**。

### 8.3 本地模型的上板门槛（不达标不上板）

- `make_cmd_dataset.py` 里每个动作**至少 20–30 条不同表述**，要含"把灯调暗一点"
  这类模糊说法；
- `score_cmd_model.py` 必须输出**混淆矩阵**，重点看"调亮/调暗""开/关"是否互混；
- **留出集准确率 ≥ 90%** 才烧进 `llm` 分区；不达标就加语料重来。

### 8.4 演示视频必须有"断网对比"

联网：语音 → S3 → 云端大模型 → 控制；断网：语音 → S3 本地模型 → miIO 局域网 →
控制。**屏幕中文 + 喇叭播报 + 被控端状态三处同时变化**才算完整证据。
被控端是**官方模拟器**这件事在旁白里说清楚（见第 6 节的风险标注）。

### 8.5 关于格式串（回答"顺手检查一遍"）

`net_miio.c` / `net_cloud.c` 里所有 `snprintf` 与 `ESP_LOGx` 都被编译器的 `-Wformat`
检查过（这次那条 `-Werror=format-extra-args` 就是它报出来的），**格式串与实参的
匹配是编译期保证**，不必人肉再数一遍。ESPLM 的下游（`esp32s3_llm`）不受影响：
miIO 只挂在网关自己的路由上，没有动共享组件。

## 9. 本地模型的路线取舍（2026-09-20 评估）

场外建议给了一批现成的意图分类模型与工具（Intento-v1-edge、ChatLM-mini-Chinese、
cardputer-ai、MASC、openclaw-zh-intents-50k、ViSpeak-Bench 等）。逐条对照我们的
约束后取舍如下——**先把"为什么不能直接用"写清楚**，省得后人再试一遍。

### 9.1 两条硬约束

1. **运行时是 llama2.c 格式 + 闭集动作 JSON。** S3 上跑的是从 llama2.c 移植的
   `espllm`，加载的是"7 个 int 头 + 权重 + 词表 blob"的打包格式。Hugging Face 的
   PyTorch/transformers 权重**不能直接上板**：要么转换成 llama2.c 格式（等于按我们
   的动作集重训），要么在 S3 上引入 transformers 运行时（内存与依赖都不允许）。
2. **许可证必须与 Apache-2.0 仓库相容。** CC BY-NC 的权重（如
   snival/intent-router-zh-setfit-v2，非商用）**不能进比赛作品**；MIT/Apache 的项目
   可以借鉴做法，但把外部权重直接放进固件仍需谨慎：模型分区只有 8 MB，而且它没有
   我们的动作集，等于还是要重训。

### 9.2 真正对症的两件事（按性价比排序）

1. **用我们自己的云端模型合成语料（知识蒸馏）。** `make_cmd_dataset.py` 现在是模板
   生成，句式有上限。用云端大模型按"每个动作 ≥30 种口语说法（含模糊表达、口语碎句）"
   批量生成、人工过一遍，直接喂现有训练脚本：**零新依赖、无许可证问题、正面打
   换个说法也能懂这个痛点。**
2. **换形态：从"生成式 0.26M"改成"小分类器"。** 闭集意图分类用分类器比用生成式
   小模型更省参数也更准：字符 n-gram 哈希嵌入 + 线性/小 MLP，int8 量化后几百 KB，
   在 PC 上用 torch 训练、用**同一套留出纪律**评分；S3 侧只换掉 `espllm` 的调用点，
   **网关对板子的接口不变**（仍是 `model:"cmd"` 返回动作 JSON），板子一行不改。
   这是"泛化"问题最对症的方案。

### 9.3 不做的事

- 不把 Hugging Face 训练栈引入固件侧；不带 NC 许可的权重进作品；
- 不为"塞满 PSRAM"而堆参数——控制类任务里，分类器 + 足量语料 > 更大的生成模型；
- 不把未达 §8.3 门槛的模型烧进 `llm` 分区。

## 10. MIoT-spec（siid/piid）这条线：结论与下一步（2026-09-20 晚）

### 10.1 官方 miot-simulator 不是手写 YAML

 的设备描述**不是**像 miio 那样手写的属性表，而是

### 10.2 我们能自己做的部分（不依赖账号）

较新的米家灯具走的是标准 light spec，常用属性是固定的：

    siid 2 (light service)：piid 1 = power(bool)，piid 2 = brightness(1-100)，
                            piid 4 = color-temperature(K)
    get_properties  [{did:,siid:2,piid:1}]
    set_properties  [{did:,siid:2,piid:1,value:true}]

所以下一步是在  里加一类 **miot 动作**（ /

把对用户友好的动作（开/关/调亮/调暗/调色温）按上面的标准映射翻成 siid/piid。
这样打开台灯对两种设备都能用，而**板子侧一行都不用改**（接口仍是动作 JSON）。

### 10.3 验证路径

1. 拿到一份 spec（或手工按标准 light spec 造一份）→ 起官方 ；
2. S3 用 miot 动作打它，官方日志为证；
3. 与 miio 那条线一样：**官方代码当裁判**。

在拿到 spec 之前，本节只是计划，不是已完成项。
