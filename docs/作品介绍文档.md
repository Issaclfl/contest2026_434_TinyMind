## 2、摘要

SF32LB52-DevKit-LCD 出厂时屏幕与触摸驱动齐备，但**板载麦克风与功放完全没有系统级驱动**，应用无法访问音频硬件。本项目基于 openvela 的 `dev-ai-contest-2026` 分支，从零实现了该芯片的 NuttX 音频 lower-half 驱动：对齐 `audio_ops_s` 全部回调，配置 AUDCODEC 模拟通路与 AUDPRC 数字路由，照抄芯片厂验证过的时钟表与防爆音上电时序，并采用**私有双半暂存区承载环形 DMA** 解决缓存一致性与缓冲对齐问题。真机实测：`/dev/audio0` 正常注册；**30 秒连续录音全程 `overruns=0`（零丢包）**，落盘 1,048,576 字节，分 32 块经串口回传后**逐字节完整**（100% 无损），导出为 WAV 已在 PC 上实际播放验证。适配过程中定位并修复了 11 个缺陷，其中 5 个是**编译期完全无法发现、只在上板后暴露**的驱动逻辑缺陷；项目同时沉淀了可复用开发 Skill 一个。

**在此基础上继续往前推了两层。** 其一，把 openvela 官方的端侧 AI Agent 引擎（`packages/ai_agent`，即官网所称 **openvelaClaw**）移植到本板——官方 defconfig 原本只覆盖 QEMU、ESP32-S3、Gemini-S1 三块板，**SF32LB52 是第四块，也是 armv8-m 上的第一块**；真机实测 Agent 启动完成，36 个工具注册、Skills 系统装载、配置写入成功。其二，为这块**没有任何网卡**的板子补上了 IP 承载：芯片不带以太网 MAC、vendor 树无 WiFi 驱动、片内 USB 是 CDC ACM 串口，因此走 **UART2 上的 PPP**，PC 侧作网关；板侧 3 处改动与 PC 侧完整链路均已验证（WSL 内双 pppd 对接，LCP/IPCP 协商成功、跨链路 ping 3/3 零丢包），只差 UART2 的物理接线。**本报告如实区分"已实测"与"未完成"**：语音通道经查证依赖 Vela 媒体框架（FFmpeg + PFW 插件），在 armv8-m 上属于另一个独立工程，故只承诺文本对话，语音通道列为后续工作。

## 3、正文

### 3.1 绪论

#### 3.1.1 项目背景与问题定义

**应用场景**：openvela 面向 AIoT 与 AI 硬件，语音交互是其中最高频的交互形态。而语音交互的物理前提，是设备能稳定采集音频。SF32LB52-DevKit-LCD 是本届大赛官方提供的开发板之一，官网对其适用场景的描述明确包含「**蓝牙音频终端**」与「多媒体」。

**真实痛点**：拿到板子后我们发现一个反差——这块板子的**硬件是完整的**：

| 板上已有的音频硬件 | 状态 |
|---|---|
| 模拟 MEMS 麦克风 | 已焊接 |
| Class-D 音频功放 | 已焊接（使能脚 PA10） |
| 外接喇叭母座（≤3W/4Ω） | 已引出 |
| 片内 AUDCODEC（ADC/DAC/PGA） | 芯片内置 |
| 片内 AUDPRC（数字路由/混音/EQ） | 芯片内置 |

但**系统侧是空白的**：板级支持中 `grep audio / codec / i2s / pdm / mic` **无任何命中**——屏幕有驱动、触摸有驱动、按键有驱动，唯独音频子系统一行代码都没有。板子出厂就是"哑巴"。

这不是某个开发者的疏忽，而是**新平台适配的典型缺口**：芯片厂提供了寄存器级 HAL，操作系统侧却需要有人把标准驱动框架与这颗芯片的模拟时序对接起来。这是一件必须有人做、但很少有人愿意做的事——因为它既不属于应用开发，也不属于内核开发，处在两者之间的"最后一公里"。

#### 3.1.2 技术难点

真正动手后，难点集中在四个地方：

1. **双器件协同**：音频通路不是一颗芯片，而是 **AUDCODEC（模拟↔数字）+ AUDPRC（数字路由）** 两颗功能单元串联。前者管 PGA/ADC/DAC/喇叭驱动，后者管路由/混音/EQ/数字增益。任何一侧配错，症状都是"无声"，而不会报错。
2. **时钟树敏感**：采样精度依赖 Σ-Δ ADC 的过采样率（OSR）与斩波时钟配比，这些参数在芯片厂驱动里是一张**调好的表**。自行推算分频比的结果通常是噪声或静音。
3. **缓存一致性**：该芯片 **D-Cache 是开启的**（`CONFIG_ARMV8M_DCACHE=y`）。DMA 在 CPU 背后写内存，若不显式维护缓存，读回的是陈旧数据——这类错误在编译器看来完全合法。
4. **错误的呈现方式是"静默"**：本项目遇到的多数缺陷不产生任何日志、不复位、不报错，只是"没有输出"。定位手段只有对照实验与逐步插桩。

#### 3.1.3 创新点

**技术层面**：采用**私有双半暂存区承载环形 DMA** 的架构（详见 3.2.3）。它一次性收敛了三个典型难题——缓存一致性、缓冲物理对齐、以及 HAL 强制环形模式与"逐缓冲交付"之间的语义错配。代价仅是每 256ms 一次 8KB 内存拷贝（约 32KB/s），相对 DMA 传输本身可忽略。

**工程层面**：把"适配过程中的 11 个真实缺陷"完整记录成文档（见 3.4.4），其中多个属于**只有上板才暴露、且失败方式为静默**的类型。这些经验已沉淀为可复用 Skill。

**交互/产品层面**：提供了一条**不依赖额外硬件即可验证音频链路**的路径——通过串口把板载 tmpfs 中的 PCM 导出到 PC 重建为 WAV。这使得在没有喇叭的情况下依然能获得"可听见"的验收证据，对硬件不齐备的团队具有实用价值。

**数据流（录音方向）**：

```
声波 → MEMS 麦克风（模拟电压）
     → AUDCODEC：PGA 可编程增益（默认 12dB）→ Σ-Δ ADC（16bit）
     → AUDPRC：RX 通道路由与数字增益（0dB）
     → DMA1_Channel4：环形模式自动搬运，无需 CPU 参与
     → 驱动私有暂存区（2 × 8KiB，64 字节对齐）
       ├─ 半满中断 → 服务半区 0
       └─ 全满中断 → 服务半区 1
     → 驱动 serve_half()：invalidate D-Cache → 拷入上层 ap_buffer
     → upper(AUDIO_CALLBACK_DEQUEUE)：通知上半身"这桶满了"
     → 应用 read() / 消息队列取走
```

#### 3.2.3 关键模块设计：私有双半暂存区 + 环形 DMA

这是本作品最核心的架构决策。

**问题的三方约束**：

1. **HAL 强制环形模式**：`HAL_AUDPRC_Receive_DMA()` 内部会检查句柄的 `dest_sel` 字段，只要它不是 `AUDPRC_TX_TO_MEM` 就**自动把 DMA 设为 CIRCULAR 并挂上半满回调**（`bf0_hal_audprc.c:796`）。也就是说 HAL 期望的用法是"环形缓冲 + 半满/全满两个中断"，而**不是**"一个缓冲一次传输"。
2. **上层缓冲不保证对齐**：`ap_buffer_s` 由上半身按默认分配器给出，驱动无法约定其缓存行对齐或物理连续性。
3. **D-Cache 开启**：DMA 目标区必须显式做缓存维护，否则读到陈旧数据。

**方案**：驱动自己持有一块**双半暂存区**（2 × `CONFIG_AUDIO_BUFFER_NUMBYTES` = 2 × 8KiB，64 字节对齐），用它承载环形 DMA；每次半满/全满中断各服务一个半区，恰好对应上层一个缓冲：

```
DMA 环形写入 → [半区0 8KiB][半区1 8KiB]
                 ↑半满中断    ↑全满中断
                 各交付/取用一个上层缓冲
```

**收益**：缓存维护范围收敛到"我们自己的、已知对齐的一块内存"，而不是散落在上层交来的任意缓冲上；同时环形模式与逐缓冲交付之间的语义错配被这层暂存彻底吸收。**代价**：每半区一次 8KiB 内存拷贝，即 32 KiB/s（16kHz/16bit/单声道），相对 DMA 传输本身可忽略。

**缓存维护的时机**（方向不同，顺序相反）：

- 采集：DMA 写内存 → **交付前 `up_invalidate_dcache()`**（丢弃 CPU 侧陈旧行）→ 再拷贝给上层
- 放音：上层写内存 → 拷入暂存区 → **`up_clean_dcache()` 推回内存** → DMA 才能读到新数据
- 启动前：对整块暂存区 `up_flush_dcache()`，避免残留脏行覆盖采集数据

#### 3.2.4 中断通路设计

```
DMAC1_CH4_IRQ (IRQn 53) → irq_attach(53 + 16)   ← NuttX 侧需加 16（Cortex-M 异常向量占用 0–15）
   → hw_rx_dma_isr() → HAL_DMA_IRQHandler(&g_audprc_hdma_rx)
      → AUDPRC_DMARxCplt / AUDPRC_DMAHalfRxCplt   （HAL 内部已挂）
         → HAL_AUDPRC_RxCpltCallback / RxHalfCpltCallback  （HAL 弱函数，本驱动覆盖）
            → hw_capture_half_ready()：invalidate 缓存 → 通知适配层
               → sf32lb52_stage_callback() → sf32lb52_serve_half()
                  → 拷入 ap_buffer → upper(AUDIO_CALLBACK_DEQUEUE)
```

放音方向对称（`DMAC1_CH1_IRQ`）。中断内只做一次有界内存拷贝加一次上层回调——NuttX 明确允许上层回调在中断上下文调用（`nuttx/audio/audio.c:1477`）。

### 3.3 核心算法与技术原理

> 说明：本作品是**系统底层驱动**，不含 AI 推理算法。本节按模板要求说明关键技术原理，以及 openvela 系统能力的运用情况。

#### 3.3.1 关键技术原理

**(1) 时钟树：照抄而非推算**

采样时钟由板上 48MHz 晶振分频得到，中间经过 Σ-Δ ADC 的过采样率（OSR）、斩波时钟、前级分频等多个参数。这些参数直接决定噪声底与直流失调，且相互耦合。本驱动**完整照抄芯片厂验证过的配置表**：

```c
static const AUDCODE_ADC_CLK_CONFIG_TYPE g_adc_clk_xtal[] = {
  { 48000, 0,  5, 0, 0, 1, 5, 0 },
  { 16000, 0, 10, 1, 0, 0, 5, 2 },
};
```

表外采样率明确返回 `-EINVAL`——**只支持真正支持的能力**，不做无法兑现的宣称。44.1kHz 家族需要音频 PLL，本驱动不支持也不上报。

**(2) 防爆音时序：为什么顺序不能错**

功放输出端的偏置电压靠电容建立。使能瞬间若输出停在偏离共模点的直流电位，喇叭线圈会收到一个直流阶跃，纸盆猛推一下——就是"砰"。**爆音与音频数据无关**（一个字节都不发也会砰），因此只能靠模拟时序消除。

放音启动严格顺序（逐行对齐芯片厂驱动）：

```
静音 → DMA 挂载 → 数字使能 → 模拟分步上电 → 等 10ms → 开功放 → 等 100ms → 解除静音
```

停止严格逆序（下电的直流跳变同样会炸）。录音则相反：**模拟先上 → MICBIAS 稳定 → 数字使能 → DMA 最后**，因为录音没有爆音问题，只需避免把上电毛刺录进数据。

**(3) `stop` 是双向握手，不是单向命令**

NuttX 音频框架的 `audio_stop()` 会把会话先置为 `AUDIO_STATE_DRAINING` **再**调用下半身的 `stop()`（`nuttx/audio/audio.c:692`），只有 `AUDIO_CALLBACK_COMPLETE` 能把它转回 `OPEN`（`:1558`）。主机侧同样在等这个信号：`nxrecorder` 的录音线程收到 `AUDIOIOC_STOP` 后**故意不退出循环**，注释写明 "we will loop until AUDIO_MSG_COMPLETE is received"。**只停硬件而不回消息，主机线程会永远等下去**——这个理解偏差曾导致整机假死（见 3.4.4 第 4 条）。

**对 openvela 的拓展与改进建议**：

1. **本作品为该平台新增了音频子系统**，填补了官方板级支持中 `grep audio` 无命中的空白。
2. **一处值得上游注意的 API 陷阱**：`nuttx/include/nuttx/spinlock.h:1538` 的守卫写成
   `#if CONFIG_SCHED_CRITMONITOR_MAXTIME_CSECTION >= 0 || defined(...INSTRUMENTATION_CSECTION)`。
   当该配置项**未定义**时，预处理按 0 参与比较，`0 >= 0` 为真 → `enter_critical_section()` 被声明为**外部函数**；而它的实现（`sched/irq/irq_csection.c`）只在 SMP 下编译。结果是**非 SMP 内核里调用它必然链接失败**。建议改为 `#ifdef` 形式或补上非 SMP 实现。本项目改用 `up_irq_save()`/`up_irq_restore()` 规避。
3. **建议在官方板级文档中补充**：本板 USB 为片内 USB CDC ACM（VID `0x38F4`）与板载 CH343 USB-UART 桥并存，两者用途不同（前者由固件提供 `/dev/ttyACM0`，后者承载 UART1 控制台与 ROM 下载），文档未明确区分，实测时容易混淆。**更具体地说**：板子有**两个 Type-C 口**——口 A 带板载 USB 转串口芯片（CH343，`1A86:55D3` → COM5 → UART1 控制台 + ROM 下载），口 B 是 USB2.0 FS，接的是**芯片原生 USB**。板级 README 写"整板由片内 USB CDC ACM（VID `0x38F4`）+ USB 直供"，指的是口 B；但文档没有把两个口的分工讲清楚，实测时极易混淆：只插口 A 时 Windows 里**枚举不到任何 `0x38F4` 设备**，一度让我们误判"芯片 USB 没有引出、IP 承载只能走 UART2"。实际上固件里 `cdcacm_initialize()` 已经把片内 CDC ACM 注册成 `/dev/ttyACM0`（`ls /dev` 可见），把线插到口 B 就是一条现成的串口。建议官方文档明确标注两个口的用途与对应设备节点。
另外板级 README 里写 UART2 为 `/dev/ttyS1`，那是 nsh 配置（多启用一路 UART3）下的编号；只启用 UART1/UART2 时实测是 `/dev/ttyS0`。还有一处使用陷阱值得写进文档：本板 SF32LB52 没有专用复位引脚，复位靠 USB-UART 桥的 RTS 拉负载开关切 VCC 实现，因此**串口工具的 RTS 行为直接决定板子是死是活**（`screen`/`cu` 会让芯片一直停在复位）。
4. **`packages` 项目未随基础 manifest 同步，导致整棵 `packages` 树不进构建**（见 3.4.7 与 3.7.1）。这一条影响的是**所有参赛队**：`apps/CMakeLists.txt:78` 的 `if(EXISTS packages/CMakeLists.txt)` 不成立，连组委会自己下发的 `app/hello_app` 骨架（映射到 `packages/demos/`）都编不进去。建议在基础 manifest 中补上该项目，或把该判断改为不依赖目录存在性。
5. **芯片 Kconfig 未声明已实现的能力**：`vendor/sifli/chips/sf32lb52/Kconfig` 从未 `select ARCH_HAVE_SERIAL_TERMIOS`，而驱动里 `TCGETS`/`TCSETS` 的代码是完整的（`sifli_uart.c:278,304`），只是被这道开关挡住——后果是运行时改不了任何串口的波特率。补一行 `select` 即可，无新增代码。这类"能力已实现但未声明"的缺口不报错、只表现为功能不可用，建议在上游补齐。

#### 3.4.2 设备注册与能力上报

**第二组：上板后暴露的驱动缺陷**

**① 开机静默死住（最严重）**

- **现象**：烧录成功、回读校验逐字节一致，但板子**一个字都不输出**；换 10 种波特率、试 8 种 RTS/DTR 电平组合、按 Reset、长时间监听，始终零字节。
- **定位**：把音频初始化整段移除做**对照实验**，板子立刻正常启动到 `nsh>` → 范围锁定在音频初始化；随后在 `hw_init()` 每一步插入打印，二分到具体那一行。
- **根因**：`hw_init()` 把 `memset` 过的 codec DMA 句柄挂进了 `g_audcodec.hdma[]`。`HAL_AUDCODEC_Init()` 对非 NULL 句柄调用 `HAL_DMA_Init()`，后者第一步就是
  `HAL_ASSERT(IS_DMA_ALL_INSTANCE(hdma->Instance));`（`bf0_hal_dma.c:550`）。
  `Instance` 是 NULL，断言失败。而**本 HAL 的 `HAL_ASSERT` 无论是否定义 `USE_FULL_ASSERT`，展开都是 `while (1) {;}`**（`bf0_hal.h:419`/`:421`）——**不打印、不复位、永久空转**。
- **解决**：codec DMA 通道保持 NULL。HAL 里 `if (hacodec->hdma[i] != NULL)` 那个守卫，本就是为"未使用的通道留 NULL"设计的。
- **经验**：`xxx_Init()` 里的循环守卫（`!= NULL`）往往就是"哪些字段可以不填"的官方说明。主动去"补全"它，可能正好踩进断言陷阱。这类断言的失败方式是**静默死循环**，没有任何日志可依。

**② `HAL_AUDCODEC_Config_RChanel()` 的通道号约定**

- **现象**：录音时报 `codec Config_RChanel failed: 1`，采集永远配不起来。
- **根因**：该函数内部是 `switch (channel) { case 0: ... case 1: ... default: return HAL_ERROR; }`，写的是 `ADC_CH0_CFG` / `ADC_CH1_CFG`——**它要的是"方向内的相对通道号 0/1"**，方向由调用哪个函数（`RChanel` / `TChanel`）决定。而 `HAL_AUDCODEC_ADC_CH0` 的枚举值是 **0x02**，直接落进 `default`。（`Config_TChanel` 同样按 0/1 分支，而 `HAL_AUDCODEC_DAC_CH0` 恰好是 0，所以放音路径"碰巧"是对的——**一半对一半错最容易漏掉**。）
- **解决**：两处都传 `0`。
- **经验**：HAL 里的通道参数有两种约定（全局枚举 vs 方向内相对号），**只能以其 `switch` 分支的实际写法为准**，不能按枚举名想当然。

**③ 设备关闭后永久 busy**

- **现象**：`device /dev/audio0` 之后再录音，报 `Audio device busy`。
- **根因**：`shutdown()`（上半身在最后一个句柄关闭时调用）只拆了硬件，没清理 `reserved`/`running`/`configured`。`reserved` 一旦置位再无人清，之后任何 `reserve()` 都返回 `-EBUSY`。
- **解决**：在 `shutdown()` 里复位这三个状态位——这是唯一可靠的会话结束钩子。

**④ `stop` 之后整机假死（两阶段排查，是本次最曲折的一个问题）**

- **现象**：录音日志一切正常（`overruns=0`），但 `stop` 之后板子再无任何响应，连 `uname -a` 都不回。约 1/3 会话必现，**间歇性**。
- **第一阶段**：`audio_stop()` 先把会话置为 `AUDIO_STATE_DRAINING` 再调用下半身 `stop()`（`audio.c:692`），只有 `AUDIO_CALLBACK_COMPLETE` 能转回 `OPEN`（`:1558`）；主机侧 `nxrecorder` 的录音线程收到 `AUDIOIOC_STOP` 后故意不退出循环，注释写明 "we will loop until AUDIO_MSG_COMPLETE is received"。于是补上该回调。
- **第二阶段（关键）**：补上后成功率上升但**偶发卡死依旧**。继续追查发现真正的根因是**阻塞发送**：
  - `AUDIO_CALLBACK_COMPLETE` 最终走到上半身的 `file_mq_send()`，其优先级取 `CONFIG_AUDIO_BUFFER_DEQUEUE_PRIO`，该宏在 `audio.c:66-68` **默认值为 1**，而 `nxrecorder` 打开消息队列时**没有 `O_NONBLOCK`**——**队列满时该发送会阻塞**。
  - 而调用现场是：录音线程停在 `AUDIOIOC_STOP` ioctl 内部（即我们的 `stop()` 里），CLI 主线程停在 `pthread_join` 上，**没有任何人在排空那个队列**。队列一旦恰好满，发送永不返回 → 假死。这解释了它的间歇性——取决于那一刻队列里恰好堆了多少条待处理消息。
- **最终解决**：把 `AUDIO_CALLBACK_COMPLETE` 改为投递到**低优先级工作队列**异步发送（`work_queue(LPWORK, ...)`）。任务上下文中阻塞是合法的，且 `stop()` 能立即返回、应用随即恢复排空队列。这正是 NuttX 框架自己给 lower-half 建议的形态：enqueuebuffer 可以 "add it to a queue for processing by a background thread or worker task"（`audio.c:1450`）。
- **经验**：**在别人的调用路径上同步回调，风险比看起来大**。`file_mq_send` 默认是阻塞语义，"谁在排空这个队列"必须逐案推演；若答案是"没有人"，同步回调就是死锁。


**⑤ 设备输出能力未声明**

- **现象**：工具跳过本设备（未在录音链路暴露，但影响放音验证）。
- **根因**：`getcaps` 只声明 `AUDIO_TYPE_INPUT`。
- **解决**：改为 `AUDIO_TYPE_INPUT | AUDIO_TYPE_OUTPUT`。

#### 3.4.7 AI Agent 引擎移植（openvelaClaw）

**目标**：把 openvela 官方的端侧 AI Agent 引擎（`packages/ai_agent`，官网称 openvelaClaw）跑在 SF32LB52 上。官方 `defconfigs/` 只覆盖 QEMU（arm64）、ESP32-S3（xtensa）、Gemini-S1（armv7-a）三块板，**SF32LB52 是第四块，也是 armv8-m 上的第一块**。

**前置缺陷（影响所有参赛队）**：`apps/CMakeLists.txt:78` 是 `if(EXISTS packages/CMakeLists.txt)`，而基础 manifest 的 `packages` 项目在当前工程里没有同步下来，该文件缺失，于是**整棵 `packages` 树从不参与构建**——组委会自己发的 `app/hello_app` 骨架（映射到 `packages/demos/`）同样编不进去。从 Gitee 的 `open-vela/packages`（`dev-ai-contest-2026` 分支）取回官方文件即解决；该文件只有两行实质内容，且同时打通 CMake 与 Kconfig 两道闸门：

```cmake
nuttx_add_subdirectory()
nuttx_generate_kconfig(MENUDESC "Packages")
```

**板级适配要点**：

| 项目 | 处理 |
|---|---|
| 网络栈 | 本板原本 `# CONFIG_NET is not set`（无网卡）。Agent 需要 TCP/UDP/DNS/ICMP/netlib/cJSON，逐项开启 |
| `CONFIG_NETDEV_IFINDEX=y` | `getifaddrs()`/`freeifaddrs()` 由 `nuttx/libs/libc/net/Make.defs:37` 用该开关守卫，被 `network_manager.c` 使用；不开会在链接期报 `undefined reference` |
| 重通道全关 | `AI_AGENT_FEISHU` / `WEIXIN` / `MQTT` / `NODE` / `MCP`（照 ESP32-S3 参考配置的裁剪法，合计约 213 KB RAM） |
| 栈配置 | defconfig **只追加基线里没有的符号**。首次尝试重复定义了 `DEFAULT_TASK_STACKSIZE` 等 5 个符号（把板子的 16096 降成 4096），Kconfig 报 "set more than once"，且栈变小会在运行时变成极难查的崩溃 |

**两处工具链兼容性修复**（厂商测试用的 xtensa / arm64 工具链比 arm-none-eabi-gcc 13.2.1 宽松，以下两处在 `-Werror` 下直接编译失败）：

| 文件 | 问题 | 修法 |
|---|---|---|
| `src/core/agent_loop.c:665` | `snprintf(reply, 512, "...%s", remind_msg)`，而 `remind_msg` 最长 511 字节、前缀约 39 字节 → `-Werror=format-truncation` | 源串改为 `%.440s`，保留 512 字节的 reply 契约 |
| `src/tools/skill_loader.c:449` | `%08x` 配 `uint32_t`。**arm-none-eabi 上 `uint32_t` 是 `unsigned long`，不是 `unsigned int`** → `-Werror=format=` | 加 `(unsigned)` 转换（在 arm64/xtensa 上是空操作，故对官方平台同样正确） |

按官方仓库既有约定（已有 `fix_esp32s3.sh`、`fix_gemini_s1.sh` 两个先例），这类"无法用 defconfig 表达"的改动做成补丁交付。

#### 3.4.8 IP 承载：给一块没有网卡的板子接上网

**问题**：这块板子上没有任何网卡——vendor 树里不存在 WiFi 驱动，芯片不带以太网 MAC，片内 USB 是 CDC ACM 串口（也就是控制台）。开箱状态是 `CONFIG_NET` 关闭、整板只有一条串口调试线。**没有 IP，Agent 就够不到 LLM 端点。**

**选型**：NuttX 树里现成的串口承载有两条。SLIP（`nuttx/drivers/net/slip.c`）**走不通**——Linux 5.14 起移除了内核 SLIP 支持，PC 侧没有对端。故选 **PPP**（`apps/netutils/pppd` + `apps/examples/pppd`）。

**数据通路**：

```
板子 UART2 (PA20 RX / PA27 TX) ──3 根线── USB-TTL ──USB── Windows COMx
                                                              │ serial_tcp_bridge.py
                                                              │ TCP
                                            WSL  socat ── /tmp/ttyPPP
                                                              │ PTY
                                                          pppd  10.0.0.1 ←→ 10.0.0.2
                                                              │ ppp0
                                              iptables MASQUERADE → eth0 → 外网
```

PC 侧之所以要绕这一圈：`pppd` 要开 `/dev/ppp` 并改 iptables，只能在 WSL 里跑；而 COM 口在 Windows 上。**刻意不引入任何需要管理员权限或驱动的东西**——Windows 侧是纯用户态的 pyserial 脚本，WSL 侧是 socat + pppd。两个 TCP 方向都实测过是通的（WSL→宿主经默认网关、Windows→WSL 经 localhost 转发），脚本用自动探测的宿主地址（WSL 重启会变，不能写死）。

**板子侧有两条通路可选**（这块板有两个 Type-C 口）：

| 通路 | 板子设备节点 | 需要什么 | 状态 |
|---|---|---|---|
| 芯片原生 USB（口 B，USB2.0 FS） | `/dev/ttyACM0` | 第二条 USB-C 线 | 软件侧已核对可通（`cdcacm` 实现了 `TCSETS`，`CONFIG_SERIAL_TERMIOS` 在本工程中已开）；**尚未物理验证** |
| UART2 + 外部 USB-TTL（口 A 之外） | `/dev/ttyS0` | USB-TTL + 三根杜邦线 | 软件链路全环节已用真硬件验证 |

这里有一段值得记下的弯路：最初只把线插在口 A（带 CH343 的那个），Windows 里枚举不到任何 `0x38F4` 设备，我们据此判断"芯片 USB 没有引出、只能走 UART2"，并把这个结论写进了文档。后来查板子官网规格页才发现**口 B 接的就是芯片原生 USB**——固件里 `cdcacm_initialize()` 早已把 `/dev/ttyACM0` 注册好，插上线就是一条现成的串口。**结论下得比证据早了一步**，已按实测边界改写。这也说明"枚举不到设备"和"设备未引出"是两回事，中间还差一次插线。

**板侧 3 处改动**：

1. **`apps/examples/pppd/pppd_main.c`** —— 上游这个例程**只能连蜂窝模组**：tty 写死 `/dev/ttyS1`，连接脚本是一段 `AT+CGDCONT` / `ATD*99***1#` 的拨号对话。直连一台 PC 时没有模组可拨，那段 chat 脚本会一直等不到 `CONNECT` 而超时。改为支持 `pppd <tty> [<baud>]` 走直连。

   **为什么一定要能指定波特率**：`pppd()` 只对 tty 做 `open()`，从不调 `tcsetattr`，链路跑的是驱动初始化时的速率。本板 `CONFIG_UART_BAUD=1000000`，而很多 USB-TTL（典型如 CP2102）最高只能到 921600，1M 根本产生不出来。所以例程在交给 `pppd()` 之前先把速率设好。

2. **`apps/netutils/pppd/ppp_conf.h`** —— `PPP_RX_BUFFER_SIZE` 同时当两个用途：装一个完整 IP 包，以及在拆帧时装一个完整 AHDLC 帧。**帧比包大**：1500 的 MTU 加上协议与 FCS 字段，再算上 `0x7e`/`0x7d` 的转义膨胀（TLS 密文近似随机，约 0.8% 的字节要转义），实测尾部能到 1560 字节。1024 装不下——这是把 `NET_TUN_PKTSIZE` 调到 1500 之后才暴露的问题。

3. **`vendor/sifli/chips/sf32lb52/Kconfig`** —— 驱动里 `TCGETS` / `TCSETS` 的代码**已经写好且完整**（`sifli_uart.c:278,304`），但被 `#ifdef CONFIG_SERIAL_TERMIOS` 包着，而后者依赖 `ARCH_HAVE_SERIAL_TERMIOS`——芯片 Kconfig 从未 `select` 它。**这个能力一直存在，只是没被声明出来**，于是运行时改不了任何串口的波特率。补一行 `select` 即可，无新增代码。

**板级 defconfig 要点**：

| 符号 | 值 | 为什么 |
|---|---|---|
| `CONFIG_NET_TUN_PKTSIZE` | `1500` | **这个值就是链路 MTU**。默认只有 296，会把一次 TLS 握手的证书切成二十个包 |
| `CONFIG_NETDB_DNSSERVER_IPv4ADDR` | `0xDF050505` | 板子的 pppd 不解析对端 IPCP 的 DNS 选项（`ppp_conf.h` 没有定义 `IPCP_GET_PRI_DNS`，整个 pppd 目录也没有一处调用 `netlib_set_dns`），DNS 必须静态给；不给就是 netdb 的默认值 `10.0.0.1`，而那个地址在本板上是 PPP 对端、不是解析器 |

**不需要路由表**：`netdev_findby_ripv4addr()`（`nuttx/net/netdev/netdev_findbyaddr.c`）在路由查找失败时回退到 `netdev_default()`，后者返回设备链表里第一个 UP 且非 loopback 的设备——ppp0 一 UP 就自动是默认出口，`CONFIG_NET_ROUTE` 不必开。

**上板才发现的三个陷阱**（都写进了交付文档）：

1. **pppd 必须后台跑。** 它是个不返回的阻塞循环，前台跑会把 nsh 控制台整个占死、直到复位为止无法再输入任何命令。正确写法 `pppd /dev/ttyS0 460800 &`。
2. **别去动 RTS。** SF32LB52 没有专用复位引脚，复位是拿 USB-UART 桥的 RTS 控一个负载开关切 VCC 实现的（板子 README 有说明，`screen`/`cu` 会让芯片一直停在复位）。实测 pyserial 的默认行为在这块板上不会导致复位或掉电，因此桥脚本 open 后不碰 DTR/RTS，并验证过桥进程退出后板子照常运行。
3. **`/dev/ttyS0` 而非 README 写的 `/dev/ttyS1`。** 板子 README 的表格是 nsh 配置（多启用一路 UART3）下的编号；本工程只启用 UART1/UART2，真机实测就是 `ttyS0`。

**另一层要处理的不对称**：板子的链路 MTU 是 1500，而 WSL 虚拟网卡只有 1280。不在 SYN 上夹住 MSS，板子会按 1500 发、转发到 eth0 时直接超 MTU。`ppp_up.sh` 在 `FORWARD` 链两个方向都把 MSS 设成 `出口MTU - 40`。

#### 3.4.9 ESP32-S3 WiFi 网关 + 本地模型：把 PC 从链路里拿掉（已真机验证）

**动机**：3.4.8 的 IP 承载需要一台 PC 当对端，板子因此离不开电脑——既不符合"多设备协同"的方向，也是评审最容易挑的一点。但对端只是一个标准的 PPP 服务端加 NAT，它没有理由必须是 PC。

**做法**：新增 `board/sf32lb52_net/esp32s3_gateway/`，由一块 ESP32-S3-DevKitC-1 跑 PPP 服务端 + NAPT，把板子接上 Wi-Fi。板子侧**一行固件都不改**：同一句 `pppd /dev/ttyS0 460800 &`，以前拨接在 USB-TTL 上的 PC，现在拨 S3。对端是谁，与板子无关——这正是 PPP 作为标准协议的价值。

| 分工 | SF32LB52（openvela） | ESP32-S3 |
|---|---|---|
| 角色 | Agent 编排 + 物理世界 I/O | 网络出口 |
| 承担 | 云端大模型对话、工具调用、音频采集 | PPP 服务端 + NAPT + WiFi STA |

**分工的第二半：S3 也出算力**。网关固件里同时跑着一个 llama2.c 小模型
（stories260K，0.26M 参数，ESP-IDF 移植，推理代码与另一块固件共用一个组件
`esp32s3_common/components/espllm`），在 `http://10.0.0.1/v1` 提供 OpenAI
兼容端点——板子 Agent 的 `set_llm` 直接指向它即可。真机实测：PSRAM octal
80 MHz、CPU 240 MHz、-O2 下 **21–26 tok/s**。它的定位是**断网降级**：
Wi-Fi 上行不在时板子仍有"另一个节点的本地推理"可问，对上评审模板
"端/云职责划分（含断网/弱网降级策略）"一条。移植采用**带断言的生成脚本**
（`tools/port_llama2.py`）：6 处针对"设备上没有 mmap/文件系统"的改动逐条
锚定命中次数，上游一变就报错而不是产出半移植的文件。

**为什么服务端要自己写**：ESP-IDF 5.5.5 提供了 lwIP 的 PPP 服务端模式（`CONFIG_LWIP_PPP_SERVER_SUPPORT`），但整个树里已经没有任何 PPP 示例（旧的 `pppos_client` 已被移除，只剩一个客户端 helper），所以服务端一侧是照 `esp_netif_ppp.h` 手写的。

**过程中发现并修掉的一处 ESP-IDF 缺陷**：`components/esp_netif/CMakeLists.txt` 用 `if(CONFIG_PPP_SUPPORT)` 决定是否编译 PPP 胶水层，而 `CONFIG_PPP_SUPPORT` 只以**兼容性别名**的形式存在于生成的 `sdkconfig.h`（`#define CONFIG_PPP_SUPPORT CONFIG_LWIP_PPP_SUPPORT`，与 `CONFIG_SUPPORT_TERMIOS` 等旧名字并列）；CMake 的 `if()` 读的是从 `sdkconfig` 生成的变量，那里只有 `CONFIG_LWIP_PPP_SUPPORT`。于是这个判断恒为假，`esp_netif_lwip_ppp.c`——也就是 `esp_netif_ppp_set_params()`、`esp_netif_start_ppp()` 的所在地——从不参与编译，直到链接期才报未定义引用。这也解释了为什么 5.5.5 不再附带任何 PPP 示例。修法是把该判断指向真正存在的符号（`tools/fix_idf_ppp_gate.py`，幂等，每次编译前自动执行）。**代码本身是完整的，开启它的那个开关写错了**——与板子缺 `ARCH_HAVE_SERIAL_TERMIOS`（见 3.4.1）属于同一类缺陷。

**当前状态**：软件完成，`idf.py build` 通过（esp32s3 目标，产出固件 355 KB）；关键配置已在生成的 `sdkconfig.h` 里核对（`LWIP_PPP_SERVER_SUPPORT=1`、`LWIP_IPV4_NAPT=1`、`LWIP_IP_FORWARD=1`、PPP 阶段事件已开；VJ 头压缩、PAP/CHAP、LCP echo 按要求关闭），并核对到 `esp_netif_lwip_ppp.c.obj` 确实进入了构建产物。

**且已在真机上验证了最没底的那一半**：3.4.9 与 3.4.8 的关键差别在于**对端换成了 lwIP 的 PPP 实现**——对面不再是 Linux 的 pppd，而 NuttX 移植的 pppd 是否愿意与它谈成，是整条路线唯一真正的未知数。用"台架模式"（`GATEWAY_UPLINK=n`，只起 PPP 服务端、不开 WiFi/NAPT）把它单独隔离出来，S3 对 PC 侧 pppd 做客户端，**2026-09-18 实测通过**：LCP 双向协商成功并正常收发 Echo；IPCP 分配地址 10.0.0.1（S3）/ 10.0.0.2（客户端）正确；`ping 10.0.0.1` 20 发 20 中、零丢包、平均 20 ms；满 MTU 通路成立（1472+28=1500 字节整帧、禁分片，3/3 通过），即一次 TLS 握手不会被切成多个包。三个细节尤其值得记录——pppd 提出的 CCP（压缩）、IPv6CP、VJ 头压缩分别被 S3 以 Protocol-Reject / ConfRej 拒绝，**逐条对应 `sdkconfig.defaults` 里三个 `=n`**，说明配置真的生效而非"看起来生效"；这也同时确认了默认的 `GATEWAY_PPP_PASSIVE=y`（S3 被动监听、由板子主动发起）方向正确，无需重烧。协商日志原文与复现命令见 `docs/ESP32-S3网关台架实测证据.md`。

**且"板子 ↔ S3"最后一跳也已在真机打通（同日）**：三根杜邦线（S3 GPIO17/18
↔ 板子 PA20/PA27 + GND），板子上仍是零改动的 `pppd /dev/ttyS0 460800 &`。
板子 Agent `ask` 一句 → 请求（系统提示+工具表 15.5 KB）经 PPP 进 S3 → 本地
模型生成 → **12.4 s 返回 576 字符并显示在板子上**；全程无 PC、无互联网。
S3 重启后板侧 pppd 6.9 s 自动重拨（早先"S3 重启要重跑 pppd"的提示对这版
板侧固件不成立）。日志原文与本次实测逼出的三个修复（HTTP 分段接收、KV 缓存
越界隐患、PPP 监控任务时间单位）见 `docs/ESP32-S3网关台架实测证据.md`。

**且 Wi-Fi 上行 + NAPT 转发也已在真机验证（同日，至此 3.4.9 无未验项）**：
S3 连上 2.4 GHz 热点拿到地址后，板子 `ping 223.5.5.5` **4 发 4 中、0% 丢包、
平均 80 ms**——板子的报文经三根线上的 PPP 进入 S3，被 NAPT 翻译成 WiFi 侧
报文上公网，回程原路返回；期间本地模型端点持续在线，云端模型与本地模型对
板子是同一个地址的两种后端。这一步还逼出并修复了一个真实故障（提交 ac6f6fb）：
WiFi 驱动每建立一条 AMPDU 接收 BA 会话，就从高优先级任务直接往控制台打一行
ROM 日志（无标签、不受日志级别控制），把 460800 波特率下只有 44 ms 余量的
2 KB UART 接收环挤爆，PPP 帧被覆写后链路死亡（板子看到 `peer asked to close
the session`）——修复是关掉 AMPDU RX（对 460800 波特 PPP 毫无收益）+ 接收环
扩到 8 KB（约 170 ms 余量），修复前该配置 30 秒内必然掉线，修复后会话稳定。
日志原文见 `docs/ESP32-S3网关台架实测证据.md` §七。

**都是嵌入式实现**（板侧 NuttX 移植的 pppd，对侧 lwIP 的 PPP 服务端），这是整条

| 环节 | 怎么验的 | 结果 |

| S3 的 PPP 服务端 ↔ PC 侧 pppd | S3 烧台架固件（`GATEWAY_UPLINK=n`、PPP 走 UART0、日志输出关闭），经 FT232 桥到 PC，`ppp_up.sh` 起客户端 | **通**：LCP 双向协商成功并正常收发 Echo |

**AI 工具对开发效率的提升**：

- **源码考古**：AI 高效完成了对 NuttX 音频框架（`nuttx/audio/audio.c` 约 2000 行）、SiFli HAL（audcodec/audprc/dma）与 nxrecorder 应用的交叉阅读，定位到 `audio_stop()` 的 DRAINING 握手语义、`HAL_ASSERT` 的 `while(1)` 实现、`Config_RChanel` 的 `case 0/1` 分支约定等**关键事实**——这些若靠人工逐行阅读，耗时将是数倍。
- **调试加速**：把"逐步插桩 + 对照实验"的诊断流程自动化，四轮内定位到 4 个静默缺陷。

**遇到的问题与解决方式**：

- **AI 会"合理推断"出错误结论。** 例：AI 曾判断"在 `stop()` 里归还缓冲会导致消息队列阻塞死锁"，据此改掉了正确实现，反而引入新问题；最终通过阅读 `nxrecorder` 源码中"loop until AUDIO_MSG_COMPLETE"的注释推翻了该判断。**教训：涉及框架契约的判断必须回到源码求证，不能采信"听起来合理"的解释。**
- **AI 无法替代硬件反馈。** 全部 4 个关键缺陷都是"编译通过、上板才炸"，且失败方式为静默。AI 的价值在于快速读源码与生成候选修复，**但"板子有没有输出"只能靠实测**。
- **应对方式**：确立"**任何结论都要有证据行号**"的纪律，并在文档中区分"已验证"与"未验证"——本报告 3.5 节对未测项均明确标注。

### 3.7 总结与展望

#### 3.7.1 成果总结

1. **为 openvela 的 SF32LB52 平台从零实现了板载音频子系统**，填补了官方板级支持中音频驱动的空白，设备以标准 `/dev/audio0` 暴露，可用通用接口访问。
2. **录音链路在真机上完整跑通并有量化数据**：**30 秒连续采集全程 `overruns=0`（零丢包）**，落盘 1,048,576 字节；分 32 块经串口回传、逐块校验字节数，**完整率 100%**；导出为 WAV 后已在 PC 上实际播放，确认波形真实有效（峰值 32715 / RMS 285.8）。
3. **定位并修复了一个间歇性整机假死**——根因是驱动在 `stop()` 中同步回调上层、而该回调会向一个"此刻无人排空"的消息队列做阻塞发送。修复方式是把回调改由低优先级工作队列异步发送。**该问题现象与代码无关、纯属时序竞态，是本项目调试难度最高的一个缺陷。**
4. **适配难点 11 项逐条记录**，其中 5 项为编译期不可见的静默缺陷——这些是最有复用价值的部分，已沉淀为 Skill。
5. **交付物完整可复现**：源码、4 处生产仓改动的 `apply.sh` 与标准 diff、构建与验证脚本、验证清单、完整技术文档齐备；评委 clone 后执行一条命令即可完成集成并构建（并附仓/树一致性自动校验，确保交付物真的可编译）。
6. **把官方 AI Agent 引擎（openvelaClaw）移植到了 SF32LB52**——官方 `packages/ai_agent/defconfigs/` 只覆盖 QEMU / ESP32-S3 / Gemini-S1，**SF32LB52 是第四块，也是 armv8-m 上的第一块**。固件 2,229,560 字节，flash 占用 13.03%、sram 29.24%；真机启动完成，36 个工具注册、Skills 装载、`set_llm` 写入成功。移植中修掉两处工具链兼容性问题（`format-truncation` 与 `uint32_t` 在 arm-none-eabi 上实为 `unsigned long` 导致的 `-Werror=format=`）。
7. **为一块没有任何网卡的板子补上了 IP 承载**。这是"要跑 Agent 就必须先有 IP，而这块板子连一张网卡都没有"逼出来的工作：vendor 树里没有 WiFi 驱动、芯片不带以太网 MAC、片内 USB 是 CDC ACM 串口（也就是控制台）。SLIP 因 Linux 5.14 起移除内核支持而不可用，故选 PPP over UART2。板侧 3 处改动中有一处是**芯片 Kconfig 从未声明 `ARCH_HAVE_SERIAL_TERMIOS`**——驱动里 `TCGETS`/`TCSETS` 的代码其实一直写好了，只是被这道开关挡住、导致运行时改不了任何串口的波特率；补一行 `select` 即可，无新增代码。PC 侧刻意不引入任何需要管理员权限或驱动的东西（Windows 侧串口转 TCP，WSL 侧 socat 造 PTY 交给 pppd）。除 UART2 那三根线之外，全链路均已用真硬件验证。
8. **顺带修掉了一个挡住所有参赛队的构建缺陷**：基础 manifest 里的 `packages` 项目未同步，导致 `apps/CMakeLists.txt:78` 的 `if(EXISTS packages/CMakeLists.txt)` 不成立，**整棵 `packages` 树从不参与构建**——组委会自己发的 `app/hello_app` 骨架（映射到 `packages/demos/`）同样编不进去。

#### 3.7.2 应用前景与商业价值

**目标受众**：以 SF32LB52 为代表的中低功耗 AIoT 设备开发者——智能穿戴、蓝牙音频终端、AI 陪伴设备、家居语音助手。这类设备普遍面临"芯片能力强、系统侧驱动缺失"的处境，本作品的方法论与代码可直接复用于同芯片的其他板型（该系列另有 LCHSPI-ULP、黄山派等衍生板，共用同一颗芯片与音频子系统）。

**商业价值**：

- **降低平台门槛**：音频是语音交互的物理前提。补齐这一环后，开发者可直接在 openvela 上做语音类产品，无需从寄存器啃起。
- **可复用的适配方法论**：本作品沉淀的 Skill 与缺陷清单，可显著缩短同类芯片的适配周期。
- **成本极低**：整机音频能力仅需开发板本身（押金 50 元，提交作品后全额退还），放音可选配 5 元级 4Ω 喇叭，具备规模化落地的成本基础。
- **生态贡献属性**：驱动以 Apache 2.0 开源，具备向 openvela 上游合入的形态（结论与方法论对同系列芯片通用）。

#### 3.7.3 不足与未来工作

**如实说明当前不足**：

1. **放音链路尚未实机验证**：驱动侧放音通路（`configure_playback` / 上电时序 / DMA 发送 / 防爆音时序）已实现并通过编译与符号验证，但**因缺少 4Ω 喇叭，尚未完成实机出声测试**，故本报告不宣称放音可用。
2. **端到端时延与功耗未测**：缺少专用测试装置（声学时延、功率计），故不提供数据。
3. **采样率支持有限**：仅支持 16kHz / 48kHz 两个家族（均由 48MHz 晶振分频）；44.1kHz 家族需音频 PLL，未实现。
4. **语音通道未打通，且已查清堵在哪里**：Agent 的默认语音后端走 Vela 媒体框架（`media_recorder`），该框架建在 FFmpeg + PFW 插件之上（`frameworks/multimedia/media/`），`CONFIG_MEDIA` 依赖 `LIB_FFMPEG`——在 armv8-m 上把整套媒体守护进程移植过来是另一个独立工程，不是本次工期能覆盖的。另外语音还需要云端 ASR/TTS 凭据。**因此本作品只承诺文本对话，语音通道如实标为未完成**，不宣称「你好，openvela」已可用。
5. **原生 USB 通路有两个已知限制**（端到端本身已跑通，见 3.5.6）：其一，板子每次复位或重新烧录后 PC 侧的 COM 口会打不开，需要把线物理拔插一次，可稳定复现——探针显示 Windows 反复对 CDC 的中断通知端点（`0x83`）发 `CLEAR_FEATURE(HALT)`，该端点一直 stall，很可能是 `usbser` 建立通知管道失败所致，**已定位到这一层但未继续修**；其二，`/data` 是 tmpfs，重启后 `set_llm` 的配置要重设。另一条通路（UART2 + USB-TTL）软件链路已验证，未做物理联调——因为原生 USB 那条已经够用。
6. **tmpfs 容量需注意**：板载可写分区为 RAM 中的 tmpfs，本次 16kHz 单声道录音在约 1 MiB 处即停止增长，长时间高采样率录制需改用更大分区或外接存储。

**未来工作（按优先级）**：

1. **完成放音实机验证与防爆音复核** —— 接入 4Ω 喇叭，验证出声质量与有无爆音（首次上板正是检验逐行对齐的防爆音时序的时机）。
2. **扩充双器件协同的模型矩阵** —— 原生 USB 那条路线（路线 1）已端到端跑通并用于演示；三根杜邦线 + ESP32-S3 网关（路线 3）也已全部真机验证（板子问/S3 本地模型答、板子经 S3 的 Wi-Fi 上公网）。协同底座已闭环，下一步是给 S3 端的本地模型加量化（int8 量化器 + 封装格式已规划，见 `board/sf32lb52_net/esp32s3_common/tools/fetch_model.py` 的模型表），把 stories260K 换成更大的英文模型或中文模型。接线表与验证步骤见 `board/sf32lb52_net/README.md`。
3. **打通 Agent 的语音通道** —— 路径已探明：需要把 FFmpeg + PFW + 媒体守护进程移植到 armv8-m（`CONFIG_MEDIA` 依赖 `LIB_FFMPEG`），之后 `media_recorder` 的音频源才能落到本作品的音频驱动上；再叠加云端 ASR/TTS 凭据。届时才谈得上「你好，openvela」。
4. **让音频设备名符合生态约定** —— 目前驱动注册为 `/dev/audio0`。生态约定是 `/dev/audio/pcm0c` + `/dev/audio/pcm0p` 这一对（官方 Gemini-S1 板即如此注册，`AGENT_AUDIO_CAPTURE_DEV` / `AGENT_AUDIO_PLAYBACK_DEV` 默认值也是这两个路径，`nxrecorder`/`nxplayer` 会自动扫描 `/dev/audio/` 目录）。受硬件单实例约束（codec、PA 使能线、暂存区都是单例），改造需要在两个设备视图之间做互斥，已在本次适配中把方案论证清楚，列为下一步。
5. **补充应用层能力** —— 结合板级已启用的 LVGL 图形能力，构建"语音交互 + 屏幕反馈"的产品形态。（应用层接入所需的 `packages/CMakeLists.txt` 构建总闸已在本次适配中补回。）
6. **补齐 44.1kHz 支持** —— 需要引入音频 PLL 并重新生成时钟表。
7. **提升长时间录制能力** —— 板载 tmpfs 容量有限，可改为写入 NOR 上的文件系统分区或外接存储。

### 复现第 3 层的对端替代方案（ESP32-S3 网关）

把上一步里的 PC 换成一块 ESP32-S3-DevKitC-1，板子那侧一字不改：

```bash
# 1) S3（ESP-IDF v5.5.5）：填 Wi-Fi 凭据后编译烧录
cd board/sf32lb52_net/esp32s3_gateway
tools\set_wifi.bat           # 交互式输入 SSID/密码（不回显），只写入 gitignore 的 sdkconfig
tools\build.bat
tools\flash.bat COMx

# 2) 接线：S3 TX GPIO17→PA20 / RX GPIO18→PA27 / GND→GND（不要接 VCC）

# 3) 板子：与上面完全相同的一句
nsh> pppd /dev/ttyS0 460800 &
```

**构建位置有个坑**：ESP-IDF 的 CMake 探测编译器时会起 `cmd.exe` 子进程，而 cmd 拒绝
以 UNC 路径为当前目录，因此若工程位于 `\\wsl.localhost\` 共享路径上，链接会以
Permission denied 失败。`tools\build.bat` 检测到 UNC 路径时会自动镜像到
`%USERPROFILE%\esp32s3_gateway_build` 再构建（`sdkconfig` 与 `build/` 保留，
凭据与增量产物都不会丢）；**改代码请改仓库，镜像目录里的改动会在下次构建时被覆盖**。

台架模式（`GATEWAY_UPLINK=n`，只起 PPP、不开 Wi-Fi/NAPT）用于在接线之前单独验证
两边的 PPP 实现能否谈成，不需要 Wi-Fi 凭据；实测结果见 3.5.6。
