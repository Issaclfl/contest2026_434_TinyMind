## 2、摘要

SF32LB52-DevKit-LCD 出厂时屏幕与触摸驱动齐备，但**板载麦克风与功放完全没有系统级驱动**，应用无法访问音频硬件。本项目基于 openvela 的 `dev-ai-contest-2026` 分支，从零实现了该芯片的 NuttX 音频 lower-half 驱动：对齐 `audio_ops_s` 全部回调，配置 AUDCODEC 模拟通路与 AUDPRC 数字路由，照抄芯片厂验证过的时钟表与防爆音上电时序，并采用**私有双半暂存区承载环形 DMA** 解决缓存一致性与缓冲对齐问题。真机实测：`/dev/audio0` 正常注册，`nxrecorder` 完成 48kHz/2ch/16bit 采集，**录得 262144 字节 PCM，`overruns=0`（零丢包）**，导出到 PC 后可播放出连续真实波形。适配过程中定位并修复了 11 个缺陷，其中 4 个是**编译期完全无法发现、只在上板后暴露**的驱动逻辑缺陷。项目同时沉淀了可复用开发 Skill 一个。

**关键词**：openvela、NuttX、音频驱动、lower-half、SF32LB52、DMA、环形缓冲、防爆音

## 3、正文

### 3.1 绪论

#### 3.1.1 项目背景与问题定义

**应用场景**：openvela 面向 AIoT 与 AI 硬件，语音交互是其中最高频的交互形态。而语音交互的物理前提，是设备能稳定采集音频。SF32LB52-DevKit-LCD 是本届大赛官方提供的开发板之一，官网对其适用场景的描述明确包含「**蓝牙音频终端**」与「多媒体」。

**真实痛点**：拿到板子后我们发现一个反差——这块板子的**硬件是完整的**：

| 板上已有的音频硬件 | 状态 |
|---|---|
| 模拟 MEMS 麦克风 | 已焊接 |
| Class-D 音频功放 | 已焊接（使能脚 PA10） |
| 外接喇叭母座（≤3W/4Ω） | 已引出 |
| 片内 AUDCODEC（ADC/DAC/PGA） | 芯片内置 |
| 片内 AUDPRC（数字路由/混音/EQ） | 芯片内置 |

但**系统侧是空白的**：板级支持中 `grep audio / codec / i2s / pdm / mic` **无任何命中**——屏幕有驱动、触摸有驱动、按键有驱动，唯独音频子系统一行代码都没有。板子出厂就是"哑巴"。

这不是某个开发者的疏忽，而是**新平台适配的典型缺口**：芯片厂提供了寄存器级 HAL，操作系统侧却需要有人把标准驱动框架与这颗芯片的模拟时序对接起来。这是一件必须有人做、但很少有人愿意做的事——因为它既不属于应用开发，也不属于内核开发，处在两者之间的"最后一公里"。

#### 3.1.2 技术难点

真正动手后，难点集中在四个地方：

1. **双器件协同**：音频通路不是一颗芯片，而是 **AUDCODEC（模拟↔数字）+ AUDPRC（数字路由）** 两颗功能单元串联。前者管 PGA/ADC/DAC/喇叭驱动，后者管路由/混音/EQ/数字增益。任何一侧配错，症状都是"无声"，而不会报错。
2. **时钟树敏感**：采样精度依赖 Σ-Δ ADC 的过采样率（OSR）与斩波时钟配比，这些参数在芯片厂驱动里是一张**调好的表**。自行推算分频比的结果通常是噪声或静音。
3. **缓存一致性**：该芯片 **D-Cache 是开启的**（`CONFIG_ARMV8M_DCACHE=y`）。DMA 在 CPU 背后写内存，若不显式维护缓存，读回的是陈旧数据——这类错误在编译器看来完全合法。
4. **错误的呈现方式是"静默"**：本项目遇到的多数缺陷不产生任何日志、不复位、不报错，只是"没有输出"。定位手段只有对照实验与逐步插桩。

#### 3.1.3 创新点

**技术层面**：采用**私有双半暂存区承载环形 DMA** 的架构（详见 3.2.3）。它一次性收敛了三个典型难题——缓存一致性、缓冲物理对齐、以及 HAL 强制环形模式与"逐缓冲交付"之间的语义错配。代价仅是每 256ms 一次 8KB 内存拷贝（约 32KB/s），相对 DMA 传输本身可忽略。

**工程层面**：把"适配过程中的 11 个真实缺陷"完整记录成文档（见 3.4.4），其中多个属于**只有上板才暴露、且失败方式为静默**的类型。这些经验已沉淀为可复用 Skill。

**交互/产品层面**：提供了一条**不依赖额外硬件即可验证音频链路**的路径——通过串口把板载 tmpfs 中的 PCM 导出到 PC 重建为 WAV。这使得在没有喇叭的情况下依然能获得"可听见"的验收证据，对硬件不齐备的团队具有实用价值。

**数据流（录音方向）**：

```
声波 → MEMS 麦克风（模拟电压）
     → AUDCODEC：PGA 可编程增益（默认 12dB）→ Σ-Δ ADC（16bit）
     → AUDPRC：RX 通道路由与数字增益（0dB）
     → DMA1_Channel4：环形模式自动搬运，无需 CPU 参与
     → 驱动私有暂存区（2 × 8KiB，64 字节对齐）
       ├─ 半满中断 → 服务半区 0
       └─ 全满中断 → 服务半区 1
     → 驱动 serve_half()：invalidate D-Cache → 拷入上层 ap_buffer
     → upper(AUDIO_CALLBACK_DEQUEUE)：通知上半身"这桶满了"
     → 应用 read() / 消息队列取走
```

#### 3.2.3 关键模块设计：私有双半暂存区 + 环形 DMA

这是本作品最核心的架构决策。

**问题的三方约束**：

1. **HAL 强制环形模式**：`HAL_AUDPRC_Receive_DMA()` 内部会检查句柄的 `dest_sel` 字段，只要它不是 `AUDPRC_TX_TO_MEM` 就**自动把 DMA 设为 CIRCULAR 并挂上半满回调**（`bf0_hal_audprc.c:796`）。也就是说 HAL 期望的用法是"环形缓冲 + 半满/全满两个中断"，而**不是**"一个缓冲一次传输"。
2. **上层缓冲不保证对齐**：`ap_buffer_s` 由上半身按默认分配器给出，驱动无法约定其缓存行对齐或物理连续性。
3. **D-Cache 开启**：DMA 目标区必须显式做缓存维护，否则读到陈旧数据。

**方案**：驱动自己持有一块**双半暂存区**（2 × `CONFIG_AUDIO_BUFFER_NUMBYTES` = 2 × 8KiB，64 字节对齐），用它承载环形 DMA；每次半满/全满中断各服务一个半区，恰好对应上层一个缓冲：

```
DMA 环形写入 → [半区0 8KiB][半区1 8KiB]
                 ↑半满中断    ↑全满中断
                 各交付/取用一个上层缓冲
```

**收益**：缓存维护范围收敛到"我们自己的、已知对齐的一块内存"，而不是散落在上层交来的任意缓冲上；同时环形模式与逐缓冲交付之间的语义错配被这层暂存彻底吸收。**代价**：每半区一次 8KiB 内存拷贝，即 32 KiB/s（16kHz/16bit/单声道），相对 DMA 传输本身可忽略。

**缓存维护的时机**（方向不同，顺序相反）：

- 采集：DMA 写内存 → **交付前 `up_invalidate_dcache()`**（丢弃 CPU 侧陈旧行）→ 再拷贝给上层
- 放音：上层写内存 → 拷入暂存区 → **`up_clean_dcache()` 推回内存** → DMA 才能读到新数据
- 启动前：对整块暂存区 `up_flush_dcache()`，避免残留脏行覆盖采集数据

#### 3.2.4 中断通路设计

```
DMAC1_CH4_IRQ (IRQn 53) → irq_attach(53 + 16)   ← NuttX 侧需加 16（Cortex-M 异常向量占用 0–15）
   → hw_rx_dma_isr() → HAL_DMA_IRQHandler(&g_audprc_hdma_rx)
      → AUDPRC_DMARxCplt / AUDPRC_DMAHalfRxCplt   （HAL 内部已挂）
         → HAL_AUDPRC_RxCpltCallback / RxHalfCpltCallback  （HAL 弱函数，本驱动覆盖）
            → hw_capture_half_ready()：invalidate 缓存 → 通知适配层
               → sf32lb52_stage_callback() → sf32lb52_serve_half()
                  → 拷入 ap_buffer → upper(AUDIO_CALLBACK_DEQUEUE)
```

放音方向对称（`DMAC1_CH1_IRQ`）。中断内只做一次有界内存拷贝加一次上层回调——NuttX 明确允许上层回调在中断上下文调用（`nuttx/audio/audio.c:1477`）。

### 3.3 核心算法与技术原理

> 说明：本作品是**系统底层驱动**，不含 AI 推理算法。本节按模板要求说明关键技术原理，以及 openvela 系统能力的运用情况。

#### 3.3.1 关键技术原理

**(1) 时钟树：照抄而非推算**

采样时钟由板上 48MHz 晶振分频得到，中间经过 Σ-Δ ADC 的过采样率（OSR）、斩波时钟、前级分频等多个参数。这些参数直接决定噪声底与直流失调，且相互耦合。本驱动**完整照抄芯片厂验证过的配置表**：

```c
static const AUDCODE_ADC_CLK_CONFIG_TYPE g_adc_clk_xtal[] = {
  { 48000, 0,  5, 0, 0, 1, 5, 0 },
  { 16000, 0, 10, 1, 0, 0, 5, 2 },
};
```

表外采样率明确返回 `-EINVAL`——**只支持真正支持的能力**，不做无法兑现的宣称。44.1kHz 家族需要音频 PLL，本驱动不支持也不上报。

**(2) 防爆音时序：为什么顺序不能错**

功放输出端的偏置电压靠电容建立。使能瞬间若输出停在偏离共模点的直流电位，喇叭线圈会收到一个直流阶跃，纸盆猛推一下——就是"砰"。**爆音与音频数据无关**（一个字节都不发也会砰），因此只能靠模拟时序消除。

放音启动严格顺序（逐行对齐芯片厂驱动）：

```
静音 → DMA 挂载 → 数字使能 → 模拟分步上电 → 等 10ms → 开功放 → 等 100ms → 解除静音
```

停止严格逆序（下电的直流跳变同样会炸）。录音则相反：**模拟先上 → MICBIAS 稳定 → 数字使能 → DMA 最后**，因为录音没有爆音问题，只需避免把上电毛刺录进数据。

**(3) `stop` 是双向握手，不是单向命令**

NuttX 音频框架的 `audio_stop()` 会把会话先置为 `AUDIO_STATE_DRAINING` **再**调用下半身的 `stop()`（`nuttx/audio/audio.c:692`），只有 `AUDIO_CALLBACK_COMPLETE` 能把它转回 `OPEN`（`:1558`）。主机侧同样在等这个信号：`nxrecorder` 的录音线程收到 `AUDIOIOC_STOP` 后**故意不退出循环**，注释写明 "we will loop until AUDIO_MSG_COMPLETE is received"。**只停硬件而不回消息，主机线程会永远等下去**——这个理解偏差曾导致整机假死（见 3.4.4 第 4 条）。

#### 3.3.2 openvela 系统能力的运用

按大赛判定标准（须使用 openvela 开源项目提供的系统能力，NuttX 内核仓库除外，且至少落地图形/AI/多媒体三项之一）：

| 能力项 | 是否落地 | 说明 |
|--------|---------|------|
| **多媒体** | ✅ **本项目核心** | 音频采集与回放子系统，以 openvela 板级适配层（`vendor/sifli`）为载体实现，并纳入 openvela 统一构建系统 |
| **图形** | ✅ 板级已启用 | `CONFIG_GRAPHICS_LVGL=y`、`CONFIG_VIDEO_FB=y`、`CONFIG_SIFLI_LCD=y`，`lvgldemo` 与 `fb` 均为可直接运行的应用，构成整机图形能力 |

**用到的 openvela 组件**：板级支持包（`vendor/sifli/boards/sf32lb52/`）、统一构建系统（`build/envsetup.sh` + `build/cmake` 自定义模块）、板级配置系统（Kconfig/defconfig）、镜像打包流程。

**对 openvela 的拓展与改进建议**：

1. **本作品为该平台新增了音频子系统**，填补了官方板级支持中 `grep audio` 无命中的空白。
2. **一处值得上游注意的 API 陷阱**：`nuttx/include/nuttx/spinlock.h:1538` 的守卫写成
   `#if CONFIG_SCHED_CRITMONITOR_MAXTIME_CSECTION >= 0 || defined(...INSTRUMENTATION_CSECTION)`。
   当该配置项**未定义**时，预处理按 0 参与比较，`0 >= 0` 为真 → `enter_critical_section()` 被声明为**外部函数**；而它的实现（`sched/irq/irq_csection.c`）只在 SMP 下编译。结果是**非 SMP 内核里调用它必然链接失败**。建议改为 `#ifdef` 形式或补上非 SMP 实现。本项目改用 `up_irq_save()`/`up_irq_restore()` 规避。
3. **建议在官方板级文档中补充**：本板 USB 为片内 USB CDC ACM（VID `0x38F4`）与板载 CH343 USB-UART 桥并存，两者用途不同（前者由固件提供 `/dev/ttyACM0`，后者承载 UART1 控制台与 ROM 下载），文档未明确区分，实测时容易混淆。

#### 3.3.3 AI 算法实现

**本阶段不涉及端侧 AI 模型部署**。基于 3 天工期与单人投入的现实，我们选择**先交付可靠的能力底座**，而不是在底座未验证的情况下仓促叠加模型——后者会导致每一部分都是半成品。

#### 3.4.2 设备注册与能力上报

```c
/* 设备名必须传裸名：NuttX 会自行拼成 /dev/audio/[name] */
audio_register("audio0", audio);
```

配合 `CONFIG_AUDIO_DEV_ROOT=y` 得到 NuttX 提供的 "simple case" 路径 `"/dev/" + name` = **`/dev/audio0`**，且无需预先创建 `/dev/audio` 目录。

**能力上报**：`getcaps` 声明同时支持输入与输出方向（`AUDIO_TYPE_INPUT | AUDIO_TYPE_OUTPUT`）——驱动本就实现了完整放音通路，只声明输入会让按 OUTPUT 查找设备的宿主（如 `nxplayer`）直接跳过本设备。

**第一组：环境与构建层**

| # | 现象 | 根因 | 解决 |
|---|------|------|------|
| 1 | 链接期报 `arm-none-eabi-ar: not found` | 工具链装在 `~/arm-tc-root/usr/bin`，不在非交互 shell 的 PATH 中 | 脚本显式 `export PATH` |
| 2 | `FATAL_ERROR: Kconfig environment depends on kconfiglib`（模块其实已装） | CMake 用 `find_program(olddefconfig)` 探测，该可执行文件在 `~/.local/bin`，而 `.bashrc` 的 PATH 赋值漏掉了它 | PATH 补上 `~/.local/bin` |
| 3 | 改 defconfig 后配置**不生效**，且**产物大小与改动前完全一致** | 增量构建复用 `out/.../.config`，不重新读取 defconfig | 删除 `out/<board>_<config>` 后重新 `lunch` + `m`；**并养成核对产物大小/行数的习惯**——这是识破"编译成功但跑的是旧代码"的唯一廉价手段 |
| 4 | `undefined reference to enter_critical_section` | `spinlock.h:1538` 的 `#if CONFIG_SCHED_CRITMONITOR_MAXTIME_CSECTION >= 0` 在符号未定义时按 0 比较，`0 >= 0` 为真 → 声明为外部函数，而实现只在 SMP 下编译（建议上游修复） | 单核板级驱动改用 `up_irq_save()`/`up_irq_restore()` |
| 5 | 编译报 `expected expression before 'do'` | `dq_rem()` 是 `do{...}while(0)` 语句宏，不能出现在赋值右侧 | 改用会求值的 `dq_inqueue()` 判断，再调用 `dq_rem()` |
| 6 | 设备注册不上，`ls /dev` 永远没有音频节点 | `audio_register()` 只接受**设备名**，NuttX 自行拼成 `/dev/audio/[name]`；传入完整路径会得到 `/dev/audio//dev/audio0`，而 `inode_reserve()` 遇中间目录不存在直接返回 `-ENOENT` | 改用裸名 + `CONFIG_AUDIO_DEV_ROOT=y`，路径变为 `"/dev/" + name` |

**第二组：上板后暴露的驱动缺陷**

**① 开机静默死住（最严重）**

- **现象**：烧录成功、回读校验逐字节一致，但板子**一个字都不输出**；换 10 种波特率、试 8 种 RTS/DTR 电平组合、按 Reset、长时间监听，始终零字节。
- **定位**：把音频初始化整段移除做**对照实验**，板子立刻正常启动到 `nsh>` → 范围锁定在音频初始化；随后在 `hw_init()` 每一步插入打印，二分到具体那一行。
- **根因**：`hw_init()` 把 `memset` 过的 codec DMA 句柄挂进了 `g_audcodec.hdma[]`。`HAL_AUDCODEC_Init()` 对非 NULL 句柄调用 `HAL_DMA_Init()`，后者第一步就是
  `HAL_ASSERT(IS_DMA_ALL_INSTANCE(hdma->Instance));`（`bf0_hal_dma.c:550`）。
  `Instance` 是 NULL，断言失败。而**本 HAL 的 `HAL_ASSERT` 无论是否定义 `USE_FULL_ASSERT`，展开都是 `while (1) {;}`**（`bf0_hal.h:419`/`:421`）——**不打印、不复位、永久空转**。
- **解决**：codec DMA 通道保持 NULL。HAL 里 `if (hacodec->hdma[i] != NULL)` 那个守卫，本就是为"未使用的通道留 NULL"设计的。
- **经验**：`xxx_Init()` 里的循环守卫（`!= NULL`）往往就是"哪些字段可以不填"的官方说明。主动去"补全"它，可能正好踩进断言陷阱。这类断言的失败方式是**静默死循环**，没有任何日志可依。

**② `HAL_AUDCODEC_Config_RChanel()` 的通道号约定**

- **现象**：录音时报 `codec Config_RChanel failed: 1`，采集永远配不起来。
- **根因**：该函数内部是 `switch (channel) { case 0: ... case 1: ... default: return HAL_ERROR; }`，写的是 `ADC_CH0_CFG` / `ADC_CH1_CFG`——**它要的是"方向内的相对通道号 0/1"**，方向由调用哪个函数（`RChanel` / `TChanel`）决定。而 `HAL_AUDCODEC_ADC_CH0` 的枚举值是 **0x02**，直接落进 `default`。（`Config_TChanel` 同样按 0/1 分支，而 `HAL_AUDCODEC_DAC_CH0` 恰好是 0，所以放音路径"碰巧"是对的——**一半对一半错最容易漏掉**。）
- **解决**：两处都传 `0`。
- **经验**：HAL 里的通道参数有两种约定（全局枚举 vs 方向内相对号），**只能以其 `switch` 分支的实际写法为准**，不能按枚举名想当然。

**③ 设备关闭后永久 busy**

- **现象**：`device /dev/audio0` 之后再录音，报 `Audio device busy`。
- **根因**：`shutdown()`（上半身在最后一个句柄关闭时调用）只拆了硬件，没清理 `reserved`/`running`/`configured`。`reserved` 一旦置位再无人清，之后任何 `reserve()` 都返回 `-EBUSY`。
- **解决**：在 `shutdown()` 里复位这三个状态位——这是唯一可靠的会话结束钩子。

**④ `stop` 之后整机假死**

- **现象**：录音日志一切正常（`overruns=0`），但 `stop` 之后板子再无响应，连 `uname -a` 都不回。
- **根因**：`audio_stop()` 先把会话置为 `AUDIO_STATE_DRAINING` 再调用下半身 `stop()`（`audio.c:692`），只有 `AUDIO_CALLBACK_COMPLETE` 能转回 `OPEN`（`:1558`）。主机侧同样在等：`nxrecorder` 的录音线程收到 `AUDIOIOC_STOP` 后故意不退出循环，等 `AUDIO_MSG_COMPLETE`。
- **解决**：`stop()` 清空 `pendq` 后主动上报 `AUDIO_CALLBACK_COMPLETE`。
- **经验**：NuttX 音频框架的 `stop` 是**双向握手**——下半身必须回一个 complete 才算结束。只停硬件不回消息，主机线程会永远等下去，表现为整机假死。

**⑤ 设备输出能力未声明**

- **现象**：工具跳过本设备（未在录音链路暴露，但影响放音验证）。
- **根因**：`getcaps` 只声明 `AUDIO_TYPE_INPUT`。
- **解决**：改为 `AUDIO_TYPE_INPUT | AUDIO_TYPE_OUTPUT`。

2. **录音链路在真机上完整跑通并有量化数据**：48kHz/2ch/16bit 采集，`overruns=0`，落盘 262144 字节，导出后确认波形真实有效。
3. **适配难点 11 项逐条记录**，其中 4 项为编译期不可见的静默缺陷——这些是最有复用价值的部分，已沉淀为 Skill。
4. **交付物完整可复现**：源码、4 处生产仓改动的 `apply.sh` 与标准 diff、构建与验证脚本、验证清单、完整技术文档齐备；评委 clone 后执行一条命令即可完成集成并构建。

#### 3.7.2 应用前景与商业价值

**目标受众**：以 SF32LB52 为代表的中低功耗 AIoT 设备开发者——智能穿戴、蓝牙音频终端、AI 陪伴设备、家居语音助手。这类设备普遍面临"芯片能力强、系统侧驱动缺失"的处境，本作品的方法论与代码可直接复用于同芯片的其他板型（该系列另有 LCHSPI-ULP、黄山派等衍生板，共用同一颗芯片与音频子系统）。

**商业价值**：

- **降低平台门槛**：音频是语音交互的物理前提。补齐这一环后，开发者可直接在 openvela 上做语音类产品，无需从寄存器啃起。
- **可复用的适配方法论**：本作品沉淀的 Skill 与缺陷清单，可显著缩短同类芯片的适配周期。
- **成本极低**：整机音频能力仅需开发板本身（押金 50 元，提交作品后全额退还），放音可选配 5 元级 4Ω 喇叭，具备规模化落地的成本基础。
- **生态贡献属性**：驱动以 Apache 2.0 开源，具备向 openvela 上游合入的形态（结论与方法论对同系列芯片通用）。

#### 3.7.3 不足与未来工作

**如实说明当前不足**：

1. **放音链路尚未实机验证**：驱动侧放音通路（`configure_playback` / 上电时序 / DMA 发送）已实现并通过编译与符号验证，但**因缺少 4Ω 喇叭，尚未完成实机出声测试**，故本报告不宣称放音可用。
2. **一处未定位的偶发卡死**：3 次会话中出现 1 次 `stop` 后无响应，尚未找到根因。已知线索：发生在会话收尾路径，与 DMA 停止或中断解绑时序相关。**这是本项目最需要继续排查的问题。**
3. **端到端时延与功耗未测**：缺少专用测试装置（声学时延、功率计），故不提供数据。
4. **采样率支持有限**：仅支持 16kHz / 48kHz 两个家族（均由 48MHz 晶振分频）；44.1kHz 家族需音频 PLL，未实现。
5. **AI 应用层未落地**：按「AI 硬件产品创新」赛道的期待，理想交付应包含语音唤醒等 AI 应用。本项目受限于工期与单人投入，选择先交付可验证的能力底座，AI 应用列为后续工作。

**未来工作（按优先级）**：

1. **定位并修复偶发卡死** —— 在 `stop` 路径增加状态机校验与超时保护，复现并根因分析。
2. **完成放音实机验证与防爆音复核** —— 接入 4Ω 喇叭，验证出声质量与有无爆音（首次上板正是检验逐行对齐的防爆音时序的时机）。
3. **端侧语音唤醒（「你好，openvela」）** —— 在已验证的采集链路之上部署轻量 KWS 模型；本链路已可稳定提供 PCM，是该项工作的前提。
4. **补齐 44.1kHz 支持** —— 需要引入音频 PLL 并重新生成时钟表。
5. **补充应用层能力** —— 结合板级已启用的 LVGL 图形能力，构建"语音交互 + 屏幕反馈"的产品形态；应用层接入需先补 `packages/CMakeLists.txt` 与 `packages/Kconfig` 两道构建总闸（已在本次适配中探明）。
